# 킹 러쉬 래그돌 물리 테스트 리그

`kingrush-ragdoll-prototype-spec.md`(명세서)를 구현한 로컬 2인 물리 감각 테스트 리그. 네트워킹 없음, Steam 코드와 분리.

## 여는 법

1. Unity 6000.3.11f1에서 `Assets/Scenes/RagdollTest.unity`를 연다(메뉴 `ChessFight > Scenes > Ragdoll Test`). 2026-09-25 병합 때 랩 씬을 이 이름으로 옮겼다. 게임 쪽 연결과 네트워크 규칙은 [`Docs/Player/RAGDOLL.md`](../Player/RAGDOLL.md).
2. Play. 게임 화면을 클릭하면 마우스가 잠긴다(Esc로 해제).
3. Tab(또는 패드 Start)으로 튜닝 패널을 연다. 패널에서 바꾼 값은 `Settings/RagdollTuning.asset`에 그대로 남는다(에디터 기준).

폰 리그·프리팹·씬을 다시 만들려면 메뉴 `ChessFight > Ragdoll Lab > Rebuild Pawn + Scene`을 쓴다. 이미 있는 튜닝 값은 유지된다.

### 조작감 개선 (2026-09-26, R36, `JY-ragdoll_v2`)

사용자(기획자) 의견: 걷기·전력질주·좌클릭 태클·우클릭 잡기·등반이 "전부 미묘하게 안 좋은 느낌", 상용 게임 수준의 손맛을 원함. 아래 **조작감 녹화**로 개선 전 상태를 찍어 보고, 분석가 실험(튜닝 값 35가지)을 모아 고쳤다.

| 무엇 | 전 → 후 | 측정 (녹화·자동 점검) |
|---|---|---|
| 가속 `acceleration` | 20 → **30** | 90% 속도까지 0.37초 → **0.27초** |
| 멈춤 감속 `stopDeceleration` | 20 → **40** | 멈추기(0.3 m/s 아래까지) 0.40초 → **0.27초** |
| 몸을 끄는 앵커 `hipAnchorStrength` / 감쇠 `anchorDamperRatio` | 3000 / 0.25 → **4500 / 0.21** | 몸이 앵커보다 처지는 거리 0.24 → 0.20 m, 입력에 몸이 더 바로 붙음 |
| 충돌 넉다운 `knockdownImpulseThreshold` | 6 → **7.5 m/s** | 달리다 서 있는 폰과 부딪혀도 **안 넘어짐**(전에는 두 번 넘어짐). 전력질주로 벽에 박으면 여전히 넘어짐. 등반 점검 4개·45° 경사 점검이 이것으로 통과 |
| 버둥대기 | 물리로 손이 끊기면 탈출 → **클릭 게이지** | 아래 "버둥대기" |
| 좌클릭 | 발부터 슬라이딩 → **머리부터 다이빙, 팔을 앞으로** | 아래 "다이빙 태클" |
| 전력질주 지침 | 바닥나는 스텝에 한 번 질주와 지침이 겹침 → 수정 | |
| 등반 팔 | 시작 순간 팔이 0.46 m까지 늘어남 → 0.24 m 안 | |

마지막 두 줄은 자동 점검이 **앞에 어떤 점검이 돌았느냐에 따라** 통과·실패가 바뀌어서 찾았다(PhysX는 같은 순서로 만든 장면에서만 결과가 똑같다). 그런 점검은 운에 기대고 있다는 뜻이라 추적을 붙여 진짜 원인을 고쳤고, 등반 점검을 네 가지 다른 순서로 돌려 모두 통과했다. `-ragdollAutoTestOnly Climb,ClimbSurfaces`처럼 점검 일부만 돌릴 수 있다(메서드 이름, 쉼표로 구분).

**조작감 녹화(`-ragdollFeel`)** — `LabAutoTest.Feel.cs`. 기본 조작 13가지(달리기·멈춤·반대 방향, 카메라 돌리며 달리기, 전력질주, 점프, 부딪히기, 다이빙, 달리며 태클, 제자리 태클, 잡아 끌고 던지기, 버둥대기 두 가지, 2 m·4 m 벽 등반)를 **플레이어 카메라와 옆 카메라로 동시에** 30 fps로 찍고, 프레임마다 입력·속도·상태·스테미나를 CSV로 남긴다.

```
RagdollLab.exe -batchmode -ragdollFeel <폴더> [-ragdollFeelOnly run,dive_run] [-ragdollTuning 값.json] -screen-width 800 -screen-height 450
python -X utf8 Tools/RagdollPreview/feel_sheets.py <폴더> [--gif]
```

`feel_sheets.py`가 장면마다 0.1초 간격 연속 사진(`<장면>_sheet_N.png` 플레이어 시점, `<장면>_side_N.png` 옆 시점)과 GIF, 구간별 요약(최고 속도, 90% 도달, 멈추는 시간, 최대 기울기, 흐물한 시간, 상태 흐름)을 만든다. `-ragdollTuning`으로 **다시 빌드하지 않고** 튜닝 값만 바꿔 비교할 수 있다. 그래픽이 필요하다(`-nographics` 금지). 녹화 중에는 카메라가 게임 시간으로 따라간다(`LabCamera.GameTimeClock`; 실제 시간으로 따라가면 녹화에서 카메라가 몇 m 뒤처진다).

### 달리기와 전력질주 (2026-09-25부터)

플레이테스트에서 고른 **"크게 달리기"(9.6 m/s)는 이제 전력질주**다. Shift를 누르고 있는 동안 스테미나를 쓰며 이 속도·동작으로 뛴다. 방향키만 누르면 **따로 만든 달리기 동작**이 나온다. `Settings/RagdollTuning.asset`에 두 값이 모두 들어 있고, 랩과 `RagdollPawn` 프리팹은 이 값으로 시작한다.

| 값 | 달리기 (기본) | 전력질주 (Shift) | 명세 시작값 |
|---|---|---|---|
| 속도 | `moveSpeed` 5.5 m/s | `sprintSpeed` 9.6 m/s | 5 m/s |
| 걸음 주기 | `hopCadence` 2.9회/초 | `sprintCadence` 3.5회/초 | 0 (보폭 기준) |
| 다리 스윙 | `legSwing` 60° | `sprintLegSwing` 60° (고관절 한계, 코드에서도 60°로 막음) | 35° |
| 뒤로 찬 발 바깥으로 | `runSplay` 10° | `sprintSplay` 22° (스커트 옆으로 발이 보임) | 0 |
| 팔 | 몸 옆에서(`runArmDown` 35°) 진자처럼 앞뒤로 `armSwing` 55° | 옆으로 벌리고 앞뒤로 휘두름 `sprintArmSwing` 76° | 35° |
| 앞으로 숙임 | 골반 `runLean` 8° + 가슴 `chestLean` 10° + 딛을 때 `runDrive` 4° | 골반 `sprintLean` 12° + 가슴 `sprintChestLean` 16° + 딛을 때 `sprintDrive` 7° | 6° + 10° |
| 튀어 오름 | 다리를 따라 30%만 내려감(`runLegDrop` 0.3) → 걸음마다 약 3 cm 가볍게 뜸 | 들기 `sprintLift` 0.05 m + 벌어질 때 `sprintBob` 0.07 m (크게 뜀) | - |
| 걸음 좌우 기울기 | `stepRoll` 3° | `sprintRoll` 6° | 0 |
| 가속·회전 쏠림 최대 | `turnLean` 10° | `sprintTurnLean` 15° | 0 |
| 상체 비틀기 | `runTwist` 8° | 없음 | 0 |

- **달리기**는 걷기가 아니라 뛰는 동작이다. 다리를 관절 한계까지 휘두르고, 걸음마다 살짝 뜨고, 앞으로 숙이고 딛을 때마다 한 번 더 숙이며 팔을 펌프질한다.
- **전력질주**는 예전의 과장된 귀여운 모습을 지금의 안정된 물리 위에 다시 만든 것이다. 예전 140° 다리는 고관절(앞뒤 60~75°, 옆 35°)에 박혀 발이 우연히 옆으로 튀었고, 90°를 넘는 목표는 드라이브를 반대 방향으로 밀기도 했다. 지금은 뒤로 찬 발을 **일부러** 22° 바깥으로 차서 스커트 옆으로 보이게 하고, 상체를 깊이 숙이고(최대 약 35°), 딛을 때마다 앞으로 밀어주고, 템포를 3.5회/초로 올렸다.

### 방향 전환할 때 좌우로 흔들리던 버그

W→S, A→D처럼 반대로 바꾸거나 마우스로 방향을 돌리면 몸이 좌우로 흔들렸다.

**진짜 원인 (두 번째 수정).** 몸의 기울기가 아니라 **카메라와 앵커 스프링**이었다. 첫 수정(아래 "첫 수정")은 목표 자세만 고쳤기 때문에 플레이 영상에서는 거의 달라지지 않았다.

- 카메라가 **이동 앵커**(몸이 가려는 위치)를 따라갔다. 방향을 바꾸면 앵커는 새 방향으로 곧바로 가지만, 50 kg 몸은 스프링에 끌려 늦게 따라온다. 그 사이 앵커가 몸보다 최대 0.6 m 앞서 가고, 화면 가운데는 앵커에 붙어 있으니 **폰이 화면 가운데에서 옆으로 밀렸다가 돌아왔다.** 이게 "중심축이 흔들리는" 느낌의 정체였다. 플레이 영상에서 폰을 추적해서 찾았다. 화면이 돌지 않는 구간에서도 폰이 가운데에서 20~28 px(약 0.6 m) 벗어났다가 돌아왔다.
- 앵커 스프링(3000)의 감쇠가 300으로, 이 몸무게의 임계 감쇠(약 775)의 39%밖에 안 됐다. 그래서 방향을 바꿀 때마다 몸이 경로를 지나쳤다가 되돌아왔다. 스프링 모델로 계산하면 28 cm를 흔들리며 경로를 가로질렀다.

고친 것:

- 카메라가 **몸의 무게중심**(11개 부위의 질량 평균, 물리 스텝 사이 보간)을 따라간다(`RagdollPawn.CameraPoint`). 세로는 예전처럼 바닥 + 서 있는 높이다.
- 새 값 `anchorDamperRatio` 0.25(패널 "앵커 감쇠비"): 앵커 스프링만 임계 감쇠 근처로 올렸다. 같은 모델에서 지나침이 0이 됐다. 0으로 두면 예전처럼 전체 `damperRatio`를 쓴다.

**첫 수정 (기울기 계산).** 몸의 기울기도 반대 전환에서 옆으로 쓸고 지나가서 같이 고쳤다.

1. 달리기의 앞 숙임은 몸이 보는 방향 기준이었다. 반대로 바꾸면 몸이 180° 도는 동안 앞으로 숙인 채로 돌아서, 그 숙임이 카메라에서 보면 옆으로 쓸고 지나갔다.
2. "회전할 때 안쪽으로 기울기"를 **몸이 도는 속도**로 계산했다. 180° 제자리 회전은 최대 회전으로 잡혀 크게 기울었고, 마우스는 프레임마다 방향이 조금씩 들쭉날쭉 바뀌어서 이 값이 좌우로 떨렸다.
3. 반대로 마우스로 계속 돌 때는 원심력(5.5 m/s로 초당 120° 돌면 약 1.2 g)이 몸을 바깥으로 던지는데, 안쪽 기울기가 2° 정도라 버티지 못했다.

지금은 `RagdollPawn.LeanIntoAcceleration`이 몸이 실제로 받는 **가속도 방향으로, 월드 기준으로** 기울인다(0.1초로 부드럽게, `accelLean` 0.6, 최대 `turnLean`/`sprintTurnLean`). 브레이크는 뒤로, 출발은 앞으로, 커브는 안쪽으로. 반대 전환에서는 브레이크와 반대쪽 출발이 같은 방향이라 한 번 기울었다가 바로 선다. 앞 숙임·걸음 좌우 기울기는 **몸이 가는 방향과 보는 방향이 같을 때만** 켜진다. 반대로 바꿀 때 골반을 뒤에서 잡아채는 힘도 `anchorBrakeLeash` 0.3 m로 절반으로 줄였다.

목표 자세로 계산해 보면 반대 전환 중 카메라에서 본 옆 기울기가 달리기 13° → 4°, 전력질주 22° → 7°로 줄었다(남은 것은 걸음마다의 좌우 기울기). 새 자동 점검 `반대 방향 전환 시 좌우로 흔들리지 않음`이 지킨다.

**미리보기 도구** (`Tools/RagdollPreview`): 유니티 없이 동작을 확인하려고, 프리팹의 몸체 모양(골반·가슴 충돌 메시, 머리·손 구, 팔·다리 캡슐)을 그대로 읽어 목표 자세를 뒤·옆에서 그리는 파이썬 렌더러다. `python3 Tools/RagdollPreview/preview.py 출력폴더`로 `Settings/RagdollTuning.asset`의 값 그대로 달리기·전력질주 GIF를 만든다(numpy·scipy·pillow 필요). 물리가 아니라 목표 자세라서, 실제 게임에서는 관성 때문에 조금 더 흔들린다. `gait.py`는 `RagdollPawn`의 걸음 계산을 손으로 옮긴 것이라 C#이 바뀌면 같이 고쳐야 한다.

- 두 동작 사이는 `sprintBlendSpeed`(초당 4 = 0.25초)로 섞인다. 속도에 따라 변하는 동작은 **지금 목표 속도** 기준이라 달리기도 완성된 달리기로 보인다.
- 회전 제한(`turnRateTopSpeed`)은 전력질주 속도 기준이라 달리기가 더 날렵하게 돈다.
- 값은 패널의 "이동"·"퍼펫 포즈"·"발과 무게감" 그룹(달리기)과 "전력질주 · 스테미나" 그룹(전력질주)에서 따로 조절한다.
- 전체 값은 `LabGame.StepPresetJson`과 `Settings/preset_step.json`에 있다(둘은 같은 값). **"명세 시작값"** 버튼은 코드 기본값으로 되돌리고, **"프리셋: 달리기 5.5 · 질주 9.6 (기본)"** 버튼으로 돌아온다.

| `climbStaminaMax` | 8초 | 총량. 이름은 예전 그대로(저장 파일 호환) |

| `diveStamina` | 0.6 | 다이빙 태클 1회 |

- 바닥나면: 전력질주가 멈추고(지침. 바닥나는 그 스텝부터 멈춘다 — 예전에는 한 스텝 겹쳤다), 등반 중이면 손을 놓고, 버둥대기는 게이지가 반만 찬다.
- **스테미나 UI**(`StaminaHud`): 캐릭터 머리 오른쪽 위에 원형 게이지가 뜬다. 위에서부터 시계 방향으로 차 있고, 초록 → 노랑 → 빨강으로 변한다. 지치면 빨갛게 깜박이며 "지침"이 뜬다. 가득 찬 채 0.8초가 지나면 사라진다. 잡혔을 때는 게이지 아래에 "잡힘! 좌클릭 연타"와 탈출 막대가 뜬다. 화면 분할이면 각자의 화면에, 온라인에서는 호스트가 보낸 값으로 자기 게이지를 그린다. 씬을 고칠 필요 없이 `LabGame`이 시작할 때 붙인다.

### 다이빙 태클 (좌클릭) — 2026-09-26 다시 만듦 (R36)

사용자 의견: 예전 발부터 미끄러지는 슬라이딩은 "잠깐 흐물해지며 날아가다 치마가 바닥에 턱 걸려 넘어져서 이상하다". 요청대로 **앞으로 넘어지며 손을 뻗어 밀치려는 자세**, **일어날 때까지 흐물흐물**하게 바꿨다.

- 좌클릭하면 **머리부터 앞으로 엎어진다.** 앞으로 +3 m/s(`diveBoost`, 최고 10 m/s), 살짝 뜨고(`diveLift` 1.2 m/s, 서서 누르면 절반), 앞으로 도는 회전(`diveTip` 5 rad/s: 몸 전체의 회전 + 상체가 다리보다 빨리 나가는 속도 차이)이 처음에 한 번 들어가서 **가슴과 팔로 착지**하고 치마는 뒤로 들린다. 옆으로 기우는 회전(`diveSideTip`)은 0.
- **팔만 힘이 들어가** 진행 방향 앞·위·바깥으로 뻗는다(`DiveReach`, 팔 강성 × `diveArmStiffness` 5). 나머지 몸은 클릭한 그 스텝부터 일어날 때까지 **완전히 흐물흐물**하다(강성 0).
- 둥근 머리 때문에 미끄러지며 옆으로 굴러 등으로 뒤집히던 것은 **진행 방향을 축으로 한 회전만** 줄여서 막았다(`DampDiveRoll`, `diveRollDamping` 10/초). 옆으로 흐르는 속도도 초당 3씩 줄인다. 앞으로 엎어지는 회전과 흐물거림은 그대로다.
- 자동 점검(`다이빙: 머리부터 엎어지며 팔을 앞으로…`): 머리가 발보다 0.53 m 앞, 손이 가슴보다 0.35 m 앞, 엎드림 1.00, 등으로 뒤집힘 없음, 4.8 m 미끄러짐, 다이빙 중 가슴 강성 0 · 팔 강성 1600, 일어나며 W를 누르고 있어도 누운 채 끌려간 속도 1.2 m/s(2 미만).
- 예전 기록의 "첫 버전(머리부터 날아가는 다이빙)"은 **온몸을 35% 강성으로 굳혀** 딱딱했고 12 m 미끄러졌다. 이번 것은 팔만 잡고 몸은 흐물하며, 평지 마찰 0.35로 4~5 m에서 멈춘다.
- **평지에서는 짧다**: 마찰 0.35(`diveFriction`), 0.7초가 지나 1 m/s 아래로 느려지거나 최대 1.5초가 되면 **스스로 일어난다**(엎드린 채로 일어난다). 단 바닥에 엎드린 지 0.35초(`diveLieTime`)는 지나야 한다. 일어나는 동안은 몸이 선 만큼만 달려 나간다(`RiseFactor`).
- **내리막에서는 길다**: 내리막을 따라 미끄러지는 중에는 마찰이 0.08(`diveSlopeFriction`)로 떨어지고, 빠른 동안은 0.9초 제한 없이 계속 미끄러진다(최대 3.6초). 그래서 달려 내려가기보다 빠르다. 일어날 때 속도는 유지된다.
- 넉다운으로 세지 않는다. 다시 쓰려면 0.35초.
- **태클**: 미끄러지는 몸에 3 m/s 이상으로 부딪힌 상대는 넘어지고(`diveTackleImpact`, 일반 충돌 넉다운 7.5 m/s보다 낮음), 2.5 m/s 더 밀려나며, 바닥에 닿은 뒤 1.2초 누워 있다(`diveTackleHold`). 태클한 쪽은 상대와 부딪혀도, 바닥에 떨어져도 넉다운되지 않는다. 벽에 박으면 진짜 넉다운이 된다.
- 무언가를 잡고 있을 때의 좌클릭은 **던지기**, 잡혔을 때의 좌클릭은 **버둥대기**다.

### 방향키만 눌러도 저절로 점프되던 버그

원인이 둘이었다.

1. **점프가 겹쳐졌다.** 점프가 세로 속도를 "더했기" 때문에, 몸이 이미 튀어 오르는 중에 점프를 누르면 그만큼 더 높이 뛰었다. 이제 세로 속도를 점프 속도로 "맞춘다".
2. **땅에서 잠깐 떨어지는 순간을 공중으로 쳤다.** 크게 달리기는 골반을 최대 0.11 m 들썩이게 하는데, 접지 판정 여유가 0.1 m라 걸음마다 접지가 깜박였다. 공중이 되는 순간 (a) 앵커가 골반을 땅으로 당기던 것을 멈추고 몸을 따라 올라갔고 (b) 다리가 점프 자세로 확 접히며 바닥을 찼다. 급정지·급회전에서 한 통짜 다리가 장대처럼 몸을 들어 올리면 그대로 날아갔다.

고친 것:
- 접지 여유에 달리기 들썩임(`runLift + stepBob`)을 포함.
- 코요테 시간(0.12초) 동안은 점프하지 않은 한 계속 "땅에 있는 것"으로 보고 골반을 서 있는 높이로 당긴다. 점프 자세도 코요테 시간이 지나야(또는 점프를 눌러야) 나온다.
- **튀어오름 방지**(`launchClamp` 1.2 m/s): 땅을 딛고 있고 점프·등반·기상·피격·잡힘 같은 이유가 없을 때, 몸 전체(무게중심)가 딛고 있는 면에서 멀어지는 속도를 1.2 m/s(= 7 cm 높이)로 자른다. 면의 법선 기준이라 오르막 달리기는 그대로다. 패널 실시간 상태의 "튐 방지 N"이 몇 번 개입했는지 보여준다. 0으로 끌 수 있다.

### 3인칭 카메라

- 각 플레이어의 카메라가 **자기 폰 뒤에서** 따라간다(`LabCamera`). 마우스(또는 오른쪽 스틱)로 좌우·위아래를 돌리고 휠로 확대·축소한다. 벽에 막히면 앞으로 당겨지고, 다른 폰에는 막히지 않는다. 전력질주하면 시야각이 넓어진다(+8°).
- **흔들림 수정**: 첫 버전은 골반을 거의 그대로(0.05초) 따라가서, 걸음마다 좌우로 흔들리고 위아래로 들썩이는 골반의 움직임이 화면 전체를 흔들었다. 지금은 `RagdollPawn.CameraPoint`를 따라간다. 가로는 **몸 전체의 무게중심**(걸음마다의 좌우 흔들림은 골반의 회전이라 무게중심에는 거의 없다. 한때 이동 앵커를 따라갔는데, 방향을 바꿀 때 앵커가 몸보다 0.6 m까지 앞서 가서 폰이 화면에서 옆으로 밀렸다 — 위 "방향 전환할 때 좌우로 흔들리던 버그"), 세로는 땅 위에 서 있을 때 **바닥 + 서 있는 높이**(걸음 들썩임이 카메라에 안 들어감), 공중에서는 골반, 넘어졌을 때는 몸 전체 무게중심이다. 물리 스텝 사이를 보간해서 매 프레임 부드럽다. 가로 0.12초·세로 0.3초로 부드럽게 따라가고, 이동 방향으로 조금 앞을 봐서 뒤처짐을 반으로 줄인다(이 필터를 파이썬으로 모델링해 잰 값: 달리기 0.3 m·전력질주 0.5 m 뒤처짐, 멈출 때 10 cm 이하로 지나침).
- 로컬 2인: P2가 조작하는 순간 **화면이 좌우로 나뉘고** P2도 자기 카메라를 받는다. F2로 켜고 끈다(한 번 누르면 자동 전환은 멈춘다). P2 이동 방향은 P2 카메라 기준.
- 온라인: 각 PC의 카메라는 자기가 조작하는 폰만 따라간다. 화면 분할은 꺼진다.
- 예전 카메라는 모든 플레이어의 가운데를 비췄다. 가만히 서 있는 P2까지 화면에 넣으려고 해서 "다른 폰에 맞춰진" 것처럼 보였다.
- 자유 카메라는 그대로다(키는 2026-09-26부터 **F4**. F는 상호작용 키가 됐다).

## 값 세트 A/B 비교

명세서의 최종 산출물은 "값 세트 1개"다. 슬롯 4개(A~D)에 현재 값을 저장해 두고 즉시 바꿔 끼우며 비교한다.

| 키 | 동작 |
|---|---|
| Shift+1~4 | 현재 슬라이더 값을 A~D에 저장 |
| 1~4 | 해당 값 세트로 즉시 전환 |
| B | 저장된 세트 중 하나로 무작위 전환 |
| ] / [ | 지금 쓰는 세트에 좋음 / 별로 기록 |

- "블라인드"를 켜면 지금 어느 세트인지, 각 세트의 점수가 패널에서 숨겨진다. 한 명이 B를 눌러 바꾸고 둘이 플레이한 뒤 ] 또는 [로 평가하면, 값 이름을 모른 채 비교할 수 있다.
- 슬롯과 평가는 `%USERPROFILE%/AppData/LocalLow/ChessFightPrototype/ChessFighter/RagdollLabSlots.json`에 저장돼 다음 실행에도 남는다. 최종 값 세트는 패널의 "클립보드 복사"로 뽑는다.

## 무게감과 "볼링 핀" 문제 (측정 기반)

패널의 **"무게감 프리셋 (발로 달리는 느낌)"** 버튼 한 번이면 아래 값이 한꺼번에 들어간다.
Shift+2로 B 슬롯에 저장해 두고 1/2 키로 명세 기본값(A)과 번갈아 비교한다.

### 이 폰의 실측 치수

| 값 | 실측 | 사람 비율 |
|---|---|---|
| 키 | 1.00 m | — |
| 골반 높이 | 0.256 m = 키의 25.6% | 52% |
| 다리 길이 (허벅지 피벗→발목) | 0.179 m | 키의 약 50% |
| 무게 | 50 kg | — |

허벅지는 `RagdollPawn.cs`에서 55°로 제한되므로 한 걸음의 기하학적 최대치는
`0.179 × 2 × sin55° = 0.293 m`, 한 주기(두 걸음)가 0.586 m다.
보기 좋은 걸음 주기 2 Hz를 넣으면 **발이 땅을 정직하게 따라갈 수 있는 상한은 1.17 m/s**다.
명세의 moveSpeed는 5 m/s — **4.3배 초과**다. 그래서 움직임의 대부분이 다리와 무관한 미끄러짐이 되고,
다리 스윙을 아무리 키워도 "볼링 핀이 미끄러지는" 모습이 유지된다.

### 강성을 3배 올려도 아무 변화가 없었던 이유

`Slerp()`가 댐퍼를 스프링에 묶어 놓는다:

```
positionSpring = spring * SlerpDriveScale
positionDamper = spring * damperRatio * SlerpDriveScale
```

추종 대역폭은 `k/c = 1/damperRatio`이므로 **spring이 수식에서 정확히 소거된다.**
damperRatio 0.1 → 모든 관절이 10 rad/s(1.59 Hz)로 고정. 명령되는 걸음은 5 m/s에서 5.56 Hz라
**다리는 명령의 27%밖에 못 따라간다.** 실측: 명령 35°, 실제 최대 16° / 평균 8°.
강성은 애초에 레버가 아니었다 (2000 → 6000으로 올려도 결과가 소수점까지 동일).

### 해결: 드라이브에 목표 각속도를 알려준다 (`관절 속도 예측`)

`ConfigurableJoint.targetAngularVelocity`는 저장소에서 한 번도 대입된 적이 없었다(=0).
즉 댐퍼가 **스프링이 만들려는 바로 그 움직임을 제동하고 있었다.** 퍼펫 목표 회전의 해석적 각속도를
매 스텝 넣어주면 감쇠비·안정성·다른 드라이브를 전혀 건드리지 않고 그 제동이 사라진다.

같은 설정(strideLength 0.9, legSwing 35)에서 실측한 다리 실제 스윙 각도:

| 관절 속도 예측 | 최대 | 평균 | 자동 점검 |
|---|---|---|---|
| 0 (기존) | 16° | 8° | 20/20 |
| 0.5 | 26° | 13° | 20/20 |
| 0.85 | 36° | 20° | 20/20 |
| 1.0 | 41° | 23° | 19/20 (45° 경사에서 달리기가 구르기보다 빨라져 명세 기준 3 위반) |
| 1.5 | 58° | 33° | 19/20 (접촉 중 넉다운 발생 — 과함) |

기본값은 0(기존 동작). 프리셋은 1.0을 쓴다.

### 해결: 두 발을 모아 도약 (`boundGait`)

교대 걸음은 발이 땅을 따라가야 하지만, **도약은 체공 구간이 있어서 그 제약이 아예 성립하지 않는다.**
`boundGait` 1.0이면 두 다리가 같은 위상으로 움직이고 골반 들썩임도 주기당 2회 → 1회로 바뀐다.
0.18 m짜리 다리로 초당 몇 미터를 정직하게 가는 유일한 방법이고, 체스 말이라는 컨셉과도 맞는다.

### 빠르게 달려도 걸음이 유지되게: 도약 횟수 고정 (`hopCadence`)

걸음 주기가 `속도 ÷ 보폭`이면 속도를 올릴수록 다리가 그만큼 빨리 돌아야 한다.
6 m/s에서는 **초당 11.8번** 튕기게 되는데, 그 속도를 드라이브가 못 따라가서 튕김 높이가
**0.9 cm**로 주저앉고 리듬이 무너진다(간격 편차 53%). 겉보기엔 다시 미끄러지는 상태다.

`hopCadence`를 켜면 도약 횟수를 고정하고 **속도가 오르면 한 번에 더 멀리 뛴다.**
리듬이 속도와 분리되므로 moveSpeed를 얼마로 올려도 걸음이 유지된다.

| moveSpeed | hopCadence | 튕김/초 | 튕김 높이 | 간격 편차 | 절뚝임 | 자동 점검 |
|---|---|---|---|---|---|---|
| 3.0 | 끔 | 2.1 | 14.3 cm | 1% | 0% | 19/20 |
| 3.0 | 2.6 | 2.6 | 12.8 cm | 1% | 3% | 19/20 |
| 6.0 | **끔** | **11.8** | **0.9 cm** | **53%** | 18% | 19/20 |
| 6.0 | **2.6** | 2.6 | **12.9 cm** | **1%** | **0%** | **20/20** |
| 9.0 | 2.6 | 3.3 | 9.1 cm | 35% | 1% | 20/20 |

9 m/s까지 확인했고 리듬은 그대로다. 속도는 취향껏 올려도 된다.

### 절뚝거림의 원인은 리듬 충돌이었다

`boundGait`를 켜면 다리와 골반 들썩임이 **주기당 1회**가 되는데, 추진(`stanceThrust`)과
좌우 기울기(`stepRoll`)는 `|sin(gait)|`·`sin(gait)`이라 **주기당 2회**로 남아 있었다.
한 번은 세게 한 번은 약하게 밀리니 절뚝거린다. 수정:

- 추진: 걷기 `1.5708·|sin|` ↔ 도약 `3·(1 − 포물선)` 을 `boundGait`로 보간. **두 파형 모두 평균이 1.0**이라 최고 속도는 변하지 않는다.
- 들썩임: 사인 대신 **포물선** `4φ(1−φ)` — 던져진 몸의 실제 높이 곡선이다.
- 좌우 기울기: 두 발이 같이 움직이면 디딤발이 없으므로 `(1 − boundGait)`로 사라지게 했다.

절뚝임 측정값은 자동 점검의 `걸음 리듬` 줄에 나온다. 골반 높이의 극대점을 모아
간격·높이의 변동계수와 홀짝 번갈아 나타나는 차이를 백분율로 보여준다.

>   - 벽에 붙어 있는 동안 몸 전체를 퍼펫 자세대로 직접 배치한다(운동학). 가슴 높이에서 **지금 붙은 면 쪽으로만** 레이 3개를 나란히 쏴서(2개 이상 맞아야 함) 벽 위치를 재고, 몸은 항상 면에서 0.35 m(치마가 벽에 안 박히는 거리)에 둔다.
>   - W 위로(`climbSpeed` 평균 1.2 m/s: 손이 떨어질 때 느리고 짚는 순간 확 끌어올림), S 아래로(`climbDownSpeed` 1.6), A/D 옆으로(`climbSideSpeed` 0.9). **모서리는 옆으로 계속 누르면 돌아간다**. 바깥 모서리(벽이 끝나고 옆면이 이어짐)는 모서리 밖으로 곡선을 그리며, 안쪽 모서리(앞에 다른 면이 막아섬)는 구석으로 들어가며 0.4초 동안 새 면으로 돈다. 이때 카메라도 폰과 같이 돌아서, 누르던 키가 계속 같은 방향이다. 조작이 카메라 기준이라, 카메라가 그대로면 "오른쪽"이 새 벽 "안쪽"(= 위로 오르기)이 돼 버린다. 돌 수 있는 면이 없는 벽 끝에서는 멈춘다. (온라인 참가자 화면의 카메라는 아직 같이 돌지 않는다.)
>   - 가슴 높이에서 면이 끝나고 그 위에 설 자리가 있으면 **정해진 경로로 올라선다**(`climbTopOut` 0.45초: 턱 위로 올라간 뒤 안쪽으로). 두 손은 턱 위에 짚는다. 올라서는 후반부에는 몸을 곧게 세우고 다리를 펴고 팔을 내려서, **서 있는 자세로** 물리에 넘겨준다. 턱 안쪽 0.4 m에 내린다. 곡면 레인은 판을 쌓은 것이라 판 사이 이음매에서 레이가 빠지는데, 이것을 꼭대기로 착각하지 않게 "위를 보는 점이 벽 속이면 이음매"와 "꼭대기는 가슴보다 낮아야 함"으로 거른다.
>   - 내려가다 바닥에 닿으면 선다. 점프는 벽을 차고 뒤로 뛴다. 손을 놓으면 그 자리에서 그냥 떨어진다(몸이 실제로 벽 속에 있을 때만 밀어낸다).
>   - 손은 연출만 한다. 각 손은 벽의 한 점을 잡고 있다가, 가는 방향 기준으로 있어야 할 곳(위로 갈 때 어깨 위 `climbHandStep` 0.12 m, 내려갈 때 어깨 옆, 옆으로 갈 때 한 걸음 옆)에서 너무 멀어지면 새 점으로 뻗는다. 두 손이 번갈아 간다. 새 점은 **실제로 있는 곳만** 고른다: 면 위, 꼭대기 위면 턱에, 벽 끝을 넘으면 안쪽으로. 모든 손은 어깨에서 `climbArmReach`(0.24 m) 안이다. 팔은 손까지 살짝 늘어난다(`RagdollVisualSync`).
>   - 없앤 값: `climbPull`, `climbDamperRatio`, `climbArmRaise`, `climbArmLow`, `climbFlail`, `climbPullDepth`, `climbSlip`.
>   - 같은 로직을 파이썬으로 옮겨 연구소의 실제 벽(2·3·4 m 벽, 큰 벽 계단, 역경사, 곡면)에 대고 잰 값: 벽면 거리 항상 0.35 m 이상(벽 속 0프레임), 어깨→손 최대 0.70 m, 짚고 있는 손이 허공에 뜬 프레임 0, 2 m 벽 1.4초 만에 올라섬, 큰 벽 한 칸(3 m) 약 2.2초, 벽 끝 0.32 m 앞에서 정지, 역경사·곡면 모두 꼭대기에 올라섬, 내려가다 바닥에서 정지. **유니티에서 확인한 값이 아니다.**
>   - 자동 점검: `등반: 두 손이 번갈아 어깨 위를 짚음 (팔 안 늘어남)`, **`등반 시작: 몸이 벽 속으로 들어가지 않음`, `등반: 옆으로 가도 팔이 안 늘어나고 모서리를 돌아감`, `등반: 턱에 올라선 뒤 뒤로 떨어지지 않음`, `등반 중 손을 놓으면 그대로 떨어짐`, `등반: 꼭대기에 올라섬`, `등반: 역경사 20도 / 곡면 꼭대기에 올라섬`**.
>   - 네트워크 참가자 화면에서는 팔이 늘어나지 않는다(자세 패킷이 관절 회전만 보낸다).
> - **곡면 레인 "레벨 아래로 떨어짐"**: 벽을 뚫는 게 아니었다. 꼭대기(깊이 1 m)에 올라서서 쉰 뒤(쉰 프레임 52), 테스트가 계속 "앞으로"를 누르고 있어 레인 뒤로 달려 나갔다. 레인들은 30×30 바닥의 북쪽 끝에 붙어 있어 그 뒤가 허공이다. 빌더가 이제 레인 뒤에 바닥을 깐다. **메뉴 `ChessFight > Ragdoll Lab > Rebuild Pawn + Scene`을 한 번 실행해야 씬에 생긴다.** 자동 점검은 모양 레인 꼭대기에 올라서면 입력을 놓는다.
> - 측정값과 시도했다 버린 방법은 각 커밋 메시지에 있다.

### 버둥대기 (잡혔을 때 좌클릭 연타) — 2026-09-26 게이지로 다시 만듦 (R36)

사용자 의견: "클릭 한 번에 너무 바로 풀린다. 5~10번은 눌러야 하고, 이동키나 점프와 같이 쓰면 더 세게 반발해야 한다."

**원인(측정):** 탈출이 PhysX가 잡은 손(FixedJoint)을 끊는 순간이었다. 흔드는 힘 10~60에서는 24번 눌러도 안 풀리고, 90에서는 5번, 150(당시 값)에서는 1번이었다. 연타·반대 방향·점프 보너스가 **곱해져서** 한 번에 가슴에 40 m/s 넘는 충격이 들어가 폰이 11 m까지 튀기도 했다. 물리가 정하는 탈출은 횟수를 맞출 수 없다.

**지금:**
- 상대의 손은 흔든다고 끊어지지 않는다(`pawnGrabBreakForce` 20000, 안전장치일 뿐).
- **탈출 게이지**(`EscapeProgress`, 0~1): 좌클릭마다 `1 / struggleTaps`(9)만큼 찬다. 상대에게서 멀어지는 쪽(또는 끌려가는 반대쪽)으로 이동키를 누르고 있으면 × `struggleAwayBonus` 1.35, 클릭 0.25초 안에 점프를 눌렀으면 × `struggleJumpBonus` 1.3.
  - 측정: 가만히 **9번**, 당기며 점프 섞어 **6번**, 0.6초 간격으로 천천히 누르면 **20초가 지나도 못 빠져나감**. 버둥대는 동안 골반 최고 0.35 m(튀어 오름 없음).
- 클릭이 `struggleGrace` 0.25초 끊기면 게이지가 초당 `struggleDecay` 0.6씩 빠진다(09-27: 0.4초 · 0.35였을 때는 천천히 눌러도 약 15초면 빠져나갔다).
- 가득 차면 **붙잡은 모든 손이 풀리고**, 서로 `struggleEscapePush` 3.5 m/s로 밀려나며(잡던 쪽은 절반, 그리고 잠깐 휘청), `struggleFreeTime` 1초 동안은 누구도 다시 잡을 수 없다(`GrabImmune`).
- 잡혀 있는 동안 점프 키는 점프가 아니라 버둥대기 보너스다(예전에는 잡힌 채 점프해 상대를 끌고 날아갔다). 손이 풀리면 바로 다시 점프할 수 있다.
- 흔들림(`struggleShake` 35)은 보이는 몸부림일 뿐이다. **게이지가 찰수록 커진다**(최대 1.8배, 가슴이 좌우로 10° → 30° 들썩임). 양팔이 서로 엇박으로 파닥거린다(`struggleSwing` 95°).
- 스테미나: 1회 0.15. 바닥나도 게이지가 반만 찰 뿐 계속 버둥댈 수 있다(갇히면 재미없다).
- 머리 옆 "잡힘! 좌클릭 연타" 막대가 이 게이지를 보여 준다. 온라인에서는 방장이 게이지를 스냅샷에 실어 보내므로(1바이트, 프로토콜 v5) **참가자 화면에서도 막대가 찬다**.

### 등반 (벽 앞에서 우클릭 + 전진)

PEAK 방식. 스테미나를 쓰며 수직 벽을 오른다.

| 값 | 기본 | 뜻 |
|---|---|---|
| `climbStaminaMax` | 8초 | 스테미나 총량(초 단위) |
| `climbDrainHold` | 0.35/초 | 매달려만 있을 때 (→ 23초) |
| `climbDrainMove` | 0.9/초 | 오르내릴 때 추가 (→ 전력 등반 6.4초 ≈ 8.3 m) |
| `climbRecover` | 2.0/초 | 땅에서 회복 (→ 4초면 만충) |
| `climbSpeed` | 1.2 m/s | 오르는 속도 (평균) |
| `climbDownSpeed` / `climbSideSpeed` | 1.6 / 0.9 m/s | 내려가는 / 옆으로 가는 속도 |
| `climbTopOut` | 0.45초 | 꼭대기로 올라서는 시간 |
| `climbCadence` | 8회/초 | 손 바꿔 짚는 속도 |
| `climbHug` | 0.23 m | 벽과 골반 사이 거리 (머리가 닿기 직전) |
| `climbArmReach` | 0.24 m | 어깨→손 최대 거리 (팔 자체는 0.19 m) |
| `climbGripAngle` | 55° | 이 각도보다 가파른 면만 등반 가능 |

스테미나가 바닥나면 **손을 놓고 떨어진다**(1.2초 재잡기 쿨다운). 그래서 벽은 통과/실패가 아니라
**길이가 있는 경로**가 된다. HUD에 스테미나 바가 뜬다.

**손 조인트로 매달리지 않는다.** 처음엔 손을 FixedJoint로 벽에 붙였는데, 팔 길이가 0.25 m라
어깨 높이에 고정된 손으로는 관절 한계상 몸을 끌어올릴 수 없어 **그 자리에 매달린 채 스테미나만
소모**했다(실측: 6초에 0.01 m 상승). 지금은 가슴에서 정면으로 레이캐스트해 벽을 찾고, 컨트롤러가
몸을 올리고 손은 자세로 번갈아 뻗는다 — 대부분의 게임이 쓰는 방식이다. (지금 방식은 위 "현재 상태" 상자.)

바닥을 "벽"으로 착각하던 버그도 여기서 나왔다. 처음엔 잡은 대상이 움직이지 않는 물체이기만 하면
등반으로 쳤는데, 바닥도 조건을 만족해서 제자리 등반이 됐다. 지금은 잡은 면의 법선 각도를 본다.

## 온라인 (1단계: 2인 호스트 권위 동기화)

F3으로 온라인 패널을 연다. 스팀이 켜져 있고 로그인돼 있어야 한다(빌드에는 `steam_appid.txt`가 실행 파일 옆에 복사된다).

패널은 **처음에 닫혀 있다.** 패널이 열려 있는 동안은 버튼을 누를 수 있게 마우스가 풀려 있어서 시점 회전·좌클릭·우클릭이 전부 먹지 않는다(예전에는 기본으로 열려 있어서 "좌클릭·우클릭이 다 날아간" 것처럼 보였다). 경기가 시작되면 패널이 저절로 닫힌다.

1. 호스트: **테스트 방 만들기** → **방 번호 복사** → 상대에게 번호 전달
2. 참가자: 방 번호 칸에 붙여넣고 **참가**
3. 호스트: **시작 (2명)** → 두 PC 모두 로스터대로 폰이 생기고, 각자 자기 폰을 조작한다

두 사람은 서로 다른 스팀 계정이어야 하고, 같은 PC에서 두 개를 띄울 수는 없다.

### 방식

- 호스트만 물리를 계산한다. 참가자의 폰은 전부 `SetNetworkPuppet(true)`로 kinematic이 되고, 받은 자세만 그린다. 참가자 쪽 물리는 아예 돌지 않으므로 어긋날 여지가 없다.
- 참가자 → 호스트: 27바이트 입력(이동 방향은 월드 좌표, 점프·좌클릭·잡기·전력질주·능력 두 개·상호작용 비트, 조준 3바이트, 왕복 측정용 시각)을 60 Hz로 보낸다(R34 전에는 24바이트). 이동 방향은 참가자 자신의 카메라 기준으로 계산해서 보낸다.
- 호스트 → 참가자: 폰당 65바이트(골반 위치 6 + 관절 회전 11개 × 4 + 상태 1 + 스테미나 1 + 버둥대기 게이지 1 + ack 4)를 30 Hz로 보낸다(게이지는 09-27 R36에서 추가, magic `CFR3`, 프로토콜 v5). 상태 바이트는 8비트를 다 쓴다(상태 2 · 접지 · 잡기 · 순간이동 · 전력질주 · 지침 · 잡힘). 스테미나와 이 비트들로 참가자도 자기 스테미나 게이지를 그린다. 나머지 열 개 몸의 위치는 받는 쪽에서 계산한다. 모든 관절이 자식 원점에서 직선 운동을 잠그고 있어서 가능한 일이다.
- 참가자는 약 110 ms 지연의 버퍼에서 두 스냅샷을 보간해 그린다. 시계를 맞추는 대신 재생 속도를 ±15% 조절해 버퍼 깊이를 유지한다. 리스폰·텔레포트는 `snap` 비트로 즉시 반영한다(패킷 유실 대비 3회 반복 전송).
- 채널 31은 기존 `SteamMotion`, 채널 32가 래그돌 스트림이다. 로비·파티·입장 로직은 그대로 재사용하며 수정하지 않았다.

### 측정값 (헤드리스 `-ragdollAutoTest`, 스팀 없이 왕복 검사)

- 입력 패킷 24바이트, 스냅샷 폰 1명 85바이트 / 12명 778바이트
- 자세 복원 오차: 회전 최대 0.17°, 부위 위치 최대 4.5 cm(관절이 하중으로 늘어난 만큼), 골반 0.19 cm
- 12명 30 Hz 기준 호스트 업로드 약 2.05 Mbit/s (11명에게 전송). 20 Hz로 낮추면 약 1.37 Mbit/s

### 1단계에서 하지 않은 것

예측·보정 없음(참가자는 자기 입력도 왕복 지연 뒤에 반응한다 — 이 지연이 잡기·밀치기 재미를 해치는지 보는 것이 1단계의 목적이다), 호스트 이전 없음, 재접속 없음, 모드별 자동 매칭 없음(2단계), 대역폭 적응·거리별 전송률 조절 없음.

## 구조

- `RagdollPawn`: Rigidbody 11개(Hips·Chest·Head·Arm·Hand·Thigh·Foot) + ConfigurableJoint(Slerp). 절차적 퍼펫(`Puppet` 하위 Transform)이 매 FixedUpdate 목표 포즈를 만들고, 조인트 targetRotation이 이를 따른다. `LocomotionAnchor`(kinematic)가 입력대로 움직이고 Hips를 조인트로 끈다.
- 동적 강성: 접촉·잡기·경사·피격 중 **가장 낮은 배율**이 적용되고, `stiffnessLerpSpeed`로 보간된다. 넉다운 중에는 모든 스프링이 0이다.
- 시각 메시는 사용자가 준 Mixamo 리그(`Art/Pawn/Pawn.fbx`)를 그대로 쓰고, 빌더가 부위별로 가중치를 다시 계산한다(뼈 이름·구조 유지). 뼈는 LateUpdate에서 물리 몸을 따라간다.
- 파일: `Assets/ChessFight/RagdollLab/` (Scripts / Editor / Art / Generated / Materials / Prefabs / Settings). 씬은 `Assets/Scenes/RagdollTest.unity`. `RagdollDriver`가 게임 공통 캐릭터 계약(`ICharacterDriver`)을 구현한다.

| Slerp 드라이브 ×4 | 슬라이더 값 = 실제 N·m/rad가 되도록 positionSpring·Damper에 4를 곱함 | 이 프로젝트에서 Slerp 드라이브는 설정값의 약 1/4만 작동(상체 400 → 실측 97~100 N·m/rad). 직선·XY&Z 드라이브는 1:1 |
| 물리 120 Hz, 솔버 24회 | 패널에서 50/60/90/120 Hz, 12/16/24/40회 선택 | 60 Hz·16회에서는 다리 사슬이 몸무게를 못 받아 골반이 8 cm 주저앉음. 120 Hz·16회 이상이면 기준 높이 ±3 mm |
| 골반 직립 토크 | AddTorque 대신 앵커 조인트의 각도 드라이브로 구현 | 명시적 감쇠 토크가 60 Hz에서 불안정(서 있어도 36° 흔들림) |
| 중력 1.0배 | 명세 미지정 → Unity 기본값 | 1.5배에서는 명세 시작값의 상체가 거의 중립 균형이 되어 뒤로 젖혀짐 |
| 발 마찰 | 서 있을 때 0.6, 이동·밀치기·피격 중 0.1 (Minimum 합산) | 한 마디 다리가 바닥을 긁어 골반을 17° 앞으로 넘어뜨림 |
| 몸통 마찰 0.05 | 치마·상체는 거의 마찰 없음 | 벽에 부딪힌 점프가 멈추지 않게 |
| 밀치기 | 팔 강성 ×5(명세) + 몸 기울기 22° + 0.6 m 내딛기 | 치마 지름(0.58 m)보다 팔이 짧아 팔만으로는 상대에 닿지 않음 |
| 피격 판정 | 밀치는 중인 몸에 닿으면 1초간 피격 배율(0.3) 적용 | 데미지·레이캐스트 없음, 결과는 물리 |
| 동적 배율의 하체 적용 | 하체·앵커에는 배율의 60%만 적용 | 100%면 잡은 쪽이 너무 약해져 끌기 불가 |
| 퍼펫 | Animator 대신 절차적 포즈 | 애니메이션 클립 없음. 나중에 Animator로 교체 가능한 구조 |
| 원격 부위 위치 오차 6 cm 허용 | 자동 점검 기준을 5 cm → 6 cm | 부위 위치는 전송하지 않고 회전 사슬로 복원한다. 팔다리가 크게 흔들릴수록 사슬 끝(손)의 오차가 커진다: 명세 기본값 1.7 cm, 무게감 프리셋 5.0 cm. 손 위치까지 보내면 폰 1명당 12바이트가 더 든다 |

- `2 m 벽 꼭대기에 올라섬` — 점검이 올라선 뒤에도 6초 동안 앞으로 달려 벽 뒤와 바닥 끝으로 떨어졌다(점검 수정: 올라서면 입력을 놓음).
