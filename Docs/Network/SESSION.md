## 1. 두 종류의 로비

| | 파티 로비 | 경기 로비 |
|---|---|---|
| 목적 | 같이 놀 친구 그룹 유지 | 양 팀 12명 수용 |
| 최대 | 6 | 12 |
| 공개 | 비공개(ID를 알면 입장 가능) | 자동 매칭은 공개, 테스트 방은 비공개 |
| ID | `Party` | `Match` |
| 주인 | 파티장 `IsLeader` | 처음엔 만든 사람 `Host`. 시작 전 대기실(입장 화면)에서도 PC 성능 1등이 들어오면 그 PC로(R159 · R294), 시작 때 가장 적합한 PC로, 경기 중 방장이 사라지면 후계자로 옮겨 간다([HOST](HOST.md)). (R533) 이 주인이 **물리 담당 PC**이고, 시작 · 강퇴 같은 관리는 따로 **방장**(`Manager`, 방을 만든 사람)이 한다 → §10 |
| 경기 취소 시 | 유지 | 나감 |

한 사람은 자기 파티 로비에 남은 채로 경기 로비에도 들어간다. 파티장과 경기 호스트는 같을 수도 다를 수도 있다.

`Busy` = 비동기 요청 중 ∨ 검색 중 ∨ 경기 방 안 ∨ 파티 `route`가 `idle`이 아님.

## 2. 시작과 초대

- `Initialize()`: App ID 준비(`EnsureAppId`, R523) → Packsize/DLL 검사 → `SteamAPI.InitEx()` → Self ID → `InitRelayNetworkAccess()` → 콜백 등록(로비 채팅, 초대 `GameLobbyJoinRequested_t`, Rich Presence 참가 `GameRichPresenceJoinRequested_t`) → 실행 인자에 `+connect_lobby <ID>`가 있으면 그 파티로, 없으면 1인 파티 생성.
- App ID(R523): Steam은 자기가 띄우지 않은 프로그램에게서 App ID를 환경 변수 `SteamAppId`나 게임 옆 `steam_appid.txt`로만 받는다. 둘 다 없으면 `EnsureAppId`가 초기화 전에 `SteamAppId`를 넣는다(exe 옆 `steam_appid.txt` → 없으면 `SteamSession.DevAppId` 480). Steam이 띄운 경우(변수가 이미 있음)와 에디터(작업 폴더 = 프로젝트 루트, 파일 있음)는 건드리지 않는다. 빌드에는 `SteamAppIdBuildStep`(Editor)이 파일을 복사한다. 자체 App ID가 생기면 두 숫자를 바꾸고, Steam 밖에서 켠 사본을 Steam으로 다시 띄울지(`RestartAppIfNecessary`) 정한다.
- 초기화 실패 → HUD에 한국어 이유(Steam 클라이언트가 오래됨 / 그 밖은 "Steam을 실행하고 로그인한 뒤 다시 연결", App ID 함께), Steam이 준 영어 이유는 `[ChessFight] Steam 초기화 실패` 경고로 로그(빌드는 Player.log)에 → HUD `Steam 다시 연결` → `Retry()`.
- 초대: 게임 내 친구 패널의 `InviteToParty(friend)`(= `InviteUserToLobby`). 예비로 `Invite()`(오버레이).
- (R529) 받은 초대: `LobbyInvite_t` → `Invites`(보낸 사람 · 파티 · 받은 시각, `InviteLasts` 5분, 최대 `InvitesKept` 3개, 보낸 사람 · 파티마다 하나) + 파티 채팅 알림 줄(경기 화면에도). 로비는 가장 새 초대를 카드로(`AcceptInvite` = `JoinParty`, `DeclineInvite`). Steam 오버레이에서 수락(`GameLobbyJoinRequested_t`)도 그대로. 전에는 오버레이 수락 전까지 게임이 초대를 몰랐다.
- **Rich Presence(M5):** 파티가 한가할 때 `connect = "+connect_lobby <파티ID>"`, `status = "로비에서 대기 중 · 파티 n/6"`. 검색·경기 중에는 `connect`를 지우고 `status`만 "<모드> 매칭 찾는 중 / <모드> 대기실 / <모드> 경기 중". 친구의 `status`는 로비 친구 카드에 이름 아래 줄로 보인다(`FriendInfo.Detail`). 값이 바뀔 때만 설정한다. 종료 때 `ClearRichPresence()`. 파싱은 `SteamSession.ParseConnect`.
- **버전 검사:** 입장한 로비의 `kind`, `protocol`, `build`를 `Incompatibility()`가 확인한다. 파티가 다른 버전이면 나와서 "게임 버전이 다릅니다 (내 버전 X / 상대 Y)"를 보여 주고 **새 1인 파티**를 만든다(옛 코드는 파티 없이 남았다).

## 3. 자동 매칭 알고리즘

별도 매칭 서버가 아니라 Steam 로비 검색 위에 만든 정책이다.

1. 파티장만 `FindMatch()`. 파티원 배열을 정렬해 `queuedHumans`로 고정하고, 파티 봇을 붙여 `queuedMembers`를 만든다. **파티 모드도 `queuedMode`로 고정한다.** 새 ticket, 각 파티원의 `cancel` 기준값 기록.
   - 릴리스 빌드에서 파티 봇이 있으면 공개 매칭을 거부한다(M6, `BotsBlockPublicMatch`).
2. 파티 추가 입장을 잠그고 `route=search`. 파티원은 이를 보고 기다린다.
3. 검색 필터: `protocol`, **`build`**, `kind=match`, **`open=1`**(대기실, 또는 빈자리가 있는 시작한 경기. v13까지는 `phase=waiting`), `private=0`, **`mode`(= 파티 모드)**, 사람 수만큼 빈자리, 기본 거리, 최대 50개. 그래서 **다른 모드의 방은 검색되지 않는다**(방 합치기 검색도 같은 필터).
4. 결과의 `free0`/`free1`을 보고 **한 팀에 파티 전체(봇 포함)가 들어가는 방**만 후보로 남긴다.
5. ~~**빈자리가 있는 시작한 경기를 먼저**, 그다음~~ 로비 ID 오름차순으로 시도(R538: 시작한 경기는 검색에 나오지 않고, 결과에 있어도 건너뛴다). 검색 결과는 오래됐을 수 있어 입장이 최종 승인은 아니다.
6. 파티장이 먼저 입장해 호스트에 예약을 요청하고, 승인된 뒤에만 `route=<경기ID>`로 바꿔 파티원이 따라오게 한다.
7. 빈 결과가 두 번이면 자기 경기 로비를 만든다. 재시도는 1~3초 무작위, 검색 실패는 4초 뒤.
8. 자기 파티만 있는 공개 대기 방의 호스트는 약 6초 뒤, 이후 약 8초마다 **더 작은 로비 ID**의 방을 찾아 옮긴다(동시 생성 수렴). **빈자리가 있는 시작한 경기는 ID와 상관없이** 옮겨 간다(혼자 기다리던 사람도 빈자리를 채우게). (R538: '빈자리가 있는 시작한 경기로 옮겨 간다'는 없어졌다.)
9. 예약이 정확히 12이고 모두 입장 완료면 공개 경기를 자동 시작한다.
10. **(R525) 개발 빌드의 공개 방은 1 대 1부터**(사용자 11-09 "1대1로도 테스트 가능하도록 임시 조치", `SteamSession.MinTeamToStart` = 개발 빌드 1, 출시 빌드 3). **방에 들어와 아직 자리를 못 받은 사람이 있으면 시작이 기다린다**(`SeatingJoiners`, 한 사람당 최대 `JoinGrace` 8초, 입장 화면 "방에 들어온 n명이 자리를 받는 중이에요"): 전에는 시작이 방을 닫아, 대기실 방장 넘김 중에 들어와 요청이 늦게 처리된 사람이 "파티 전체가 들어갈 자리가 없습니다"나 28초 뒤 "입장 승인이 시간 초과되었습니다"로 튕겼다(모의 6인, 방 주인 이전 1~3초). 아래 R148의 "3명 이상"은 출시 빌드 기준. **(R540, 임시) 지금은 출시 빌드도 같다**: 게임이 `AllowPublicBots`를 모든 빌드에서 켠다(`NetworkRuntime.TestRulesInEveryBuild`, 팀의 테스트 빌드가 출시 빌드라서). 그 상수를 `false`로 돌리면 이 줄의 원래 규칙(개발 빌드만)으로 돌아간다.
11. **(R148) 폰 러쉬 공개 방은 12명 전에도 시작할 수 있다:** 두 팀이 **각각 3명 이상이고 인원이 같으며**(3 대 3, 4 대 4, 5 대 5) 모두 입장 완료면 방장의 입장 화면에 "게임 시작" 버튼이 켜진다(`TeamReservations.ReadyEarly`, `SteamSession.CanStartEarly`). 누르면 지금 인원으로 시작하고, 빈자리 채우기는 그 시작 인원까지만이다(§8). 12명이 차면 예전처럼 자동 시작. 다른 모드는 그대로 12명. 봇 규칙은 바뀌지 않았다(예약된 봇도 인원에 들어감).
12. **(R533) '게임 시작'은 방장(관리)의 것**: 방을 만든 사람(양도받은 사람)의 화면에만 버튼이 있다. 방장이 물리 담당 PC가 아니면 누른 것이 방 채팅 요청(`manage` · `start`)으로 물리 담당 PC에 가고, 그 PC가 9 ~ 11의 조건(인원, 자리를 받는 중인 사람)을 자기 장부로 다시 확인한 뒤 시작한다(§10). **사용자 매칭 규칙 1 ~ 2**(11-10: 팀마다 3명 이상 · 같은 인원이면 방장이 시작 → 3 대 3으로 시작한 방은 6자리 · 4 대 4는 8 · 5 대 5는 10 · 6 대 6은 12, 나간 자리만 출발 뒤 4분 안에 매칭 중인 사람으로 채움, 꽉 찬 방 대신 새 방)는 9 ~ 11과 §8에 이미 있던 규칙이라 코드는 그대로 두고 모의 테스트 4개(`Matching rules 1 ~ 2` · `Matching rule 1-4` 3개, 출시 빌드 기준 `MinTeamToStart` 3)로 고정했다. 개발 빌드의 1 대 1부터(R525)는 그대로다. **(R538) 규칙 1-2는 같은 날 바뀌었다: 나간 자리는 그 사람만 돌아올 수 있고 매칭 중인 다른 사람은 못 들어온다(§8).**

여러 파티가 이미 들어간 대기 방끼리는 합치지 않는다. 모의 12인 동시 검색 수렴 테스트가 실제 Steam의 수렴 시간을 보장하지는 않는다.

## 4. 파티 단위 예약

예약 요청 = 경기 로비 채팅의 UTF-8 JSON:

```json
{"kind":"reserve","ticket":"GUID","party":123,"members":[11,12,13]}
```

호스트는 채팅 발신자가 현재 로비 멤버인지 확인하고, **Steam이 알려준 발신자**를 leader로 쓴다(수신 버퍼 2048바이트).

`TeamReservations.Reserve()` 검사:
- sender·party ≠ 0, ticket 1~64자
- members 1~6명이고 sender 포함, 0·중복·다른 예약과 겹침 금지
- 같은 leader의 재요청은 party·ticket·배열이 완전히 같을 때만 동일 예약. 재요청이 만료를 연장하지 않는다
- 봇은 발신자가 될 수 없고, 봇 ID의 소유자가 발신자여야 한다
- 사용량이 적은 팀부터, 안 들어가면 반대 팀, 둘 다 안 되면 거절
- **예약 즉시 아직 입장하지 않은 파티원까지 정원에 센다.** 기한 25초
- (11-02 R297) 사람이 안 와서 예약이 풀린 발신자는 60초 동안 거절(`TeamReservations.Cooldown`, 아래 "보안 범위")
- 릴리스 빌드의 공개 방이면 봇이 포함된 요청을 거절한다(`|bots`)

결과는 `grant_<leaderID>` = `ticket|ok` / `|full` / `|expired` / `|bots`. 파티장은 자기 ticket 응답만 본다. `ok`가 아니면 다른 방을 찾는다. roster가 grant보다 먼저 와도 자기가 roster에 있으면 route를 갱신한다.

호스트가 파티원 전원의 실제 입장을 보면 `Committed=true`. 25초 안에 다 못 들어오거나, 입장 완료된 파티에서 한 명이 빠지면 **그 파티 예약 전체를 해제**한다. 봇은 로비에 들어오지 않으므로 항상 입장 완료로 친다.

예: 4+4로 각 팀 4명이면 빈자리는 4지만 새 4인 파티는 못 받는다. 3+3+2+2+1+1은 6 대 6을 채운다.

`PublishRoster()`는 예약된 사람 중 **실제 로비에 있는 사람(과 봇)만** roster에 싣는다. `free0/free1`은 예약 수로 계산한다.

보안 범위: 발신자 신원과 명단 형식은 확인하지만, 선언한 파티원이 정말 그 파티 소속인지는 독립적으로 검증하지 않는다(방장은 남의 파티 로비 명단을 볼 수 없다). 그래서 고친 클라이언트가 **지어낸 ID**를 파티원이라고 적어 자리를 25초씩 잡아 둘 수 있다(그동안 그 팀은 못 차고, 입장 완료 전 예약이 있으니 대기실은 시작도 못 한다). 예전에는 풀리자마자 새 ID로 다시 요청해 끝없이 되풀이할 수 있었다. (11-02 R297, 네트워크 작업 지시 [4]) 두 가지로 막는다. 프로토콜·패킷·방 데이터는 그대로다.

| 제한 | 대기실 | 시작한 경기의 빈자리(§8) |
|---|---|---|
| **한 발신자는 한 번에 한 그룹** | 원래 있었다: 같은 leader의 다른 요청은 거절, 이미 다른 예약에 든 사람도 새 그룹을 못 만든다 | 발신자는 바로 앉으므로 앉은 채 다시 요청해도 더 받지 못한다(원래). **새로:** 방장이 잡아 둔 자리마다 누가 요청했는지(`Backfill.Seat.Leader`) 기억해, 그 자리가 남아 있는 동안 같은 발신자의 새 요청은 `|full`이다(나갔다 다시 들어와 요청해도) |
| **사람이 안 오면 60초 쉰다**(`TeamReservations.Cooldown`) | 기한(25초) 안에 다 모이지 못해 풀린 예약(`|expired`)의 발신자 | 잡아 둔 자리가 아무도 안 와 기한(25초)을 넘기면 그 자리를 요청한 발신자 |

- 쉬는 동안의 요청은 어느 쪽이든 `|full`이다(새 응답 값 없음). 대기실에서 쉬기 시작한 사람은 그 사이에 경기가 시작돼도 (방장이 그대로면) 빈자리를 못 받는다(같은 기록을 쓴다).
- 입장을 마친 뒤 한 명이 빠져 풀린 파티는 쉬지 않는다(그 사람들은 실제로 왔다). 봇은 늘 와 있는 것으로 치므로 봇 때문에 쉬는 일은 없다. 봇 규칙(봇 ID 소유자, `ReserveBots`, 봇 예약, M6)은 그대로다.
- 정직한 파티도 파티원이 25초 안에 못 들어오면 **그 방에서만** 60초 동안 다시 예약할 수 없다(다른 방은 된다). 대기실에서는 예약이 풀리면 어차피 파티로 돌아가 매칭을 다시 눌러야 한다.
- 막는 것은 되풀이다. 한 번은 여전히 25초 동안 자리를 잡아 둘 수 있으니, 자리가 막히는 시간이 "늘"에서 "85초 중 25초"로 준다.
- 알고 있는 한계(이번에 손대지 않음): 예약 없이 경기 방(Steam 로비)에 들어와 머무는 사람은 쉬는 동안에도 로비 12자리 중 하나를 차지한다.

**이 두 기록은 방장 PC에만 둔다(결정).** 방장이 바뀌면 새 방장은 둘 다 모른다: 쉬던 발신자는 새 방장에게 한 번 더 요청할 수 있고, 넘겨받은 `held` 자리는 누가 요청했는지 모르니 그 자리로는 아무도 쉬지 않는다. 대기실 예약(`resv`)과 잡아 둔 자리(`held`) 자체는 지금처럼 넘어간다. 규칙 15(경기 상태를 방장에게만 두지 않기)를 따르지 않아도 되는 이유:
1. 경기 상태(점수·타이머·모드 상태·누가 어디 앉았나)가 아니다. 남용을 늦추는 장치일 뿐이라, 잃어도 경기나 자리 배정이 틀어지지 않는다.
2. 잃는 것이 작다. 방장이 바뀔 때마다 한 발신자가 많아야 한 번 더, 25초 동안, 한 파티 크기만큼 자리를 잡는 정도다. 방장은 시작 때, 대기실에 더 좋은 PC가 들어올 때, 나감·크래시·느림 때만 바뀌고, 참가자가 남의 방장 교체를 마음대로 일으킬 수는 없다(자기가 방장이 되면 어차피 자리 배정을 쥔다).
3. 방 데이터에 실으려면 `resv`·`held` 형식을 바꾸거나 새 키가 필요해 프로토콜을 올려야 하고, 옛 빌드와 섞이지 않게 해야 한다. 실제로 남용이 보이면 그때 방 데이터로 옮긴다.

| `starters` | 경기 | (R538, v35) 경기를 시작한 사람과 그 자리 `id:팀:자리;…`(사람만, 최대 12). 시작 때 한 번 쓴다. 이 목록의 사람만 나갔다가 자기 자리로 돌아올 수 있고, 새 물리 담당 PC도 이 값으로 같은 사람을 받는다. (R59의 `held` — 오는 중인 파티원의 잡아 둔 자리 — 는 없어졌다: 돌아오는 것은 각자) |
| `private` | 경기 | `0` 공개 / `1` 테스트 |
| `free0`, `free1` | 경기 | 대기실: 예약 반영 팀별 남은 자리. 시작 뒤: (R538) 팀별 **자리를 비운 시작 멤버 수**(`Starters.Away`, 화면의 "n명이 자리를 비움") |
| `grant_<ID>` | 경기 | 예약 결과 |
| `roster` | 경기 | `{"members":[{"id":…,"team":0,"slot":0}]}` (4096자, 최대 12, 중복·0·범위 검사) |

상태는 단일 enum이 아니라 `pending`, `Searching`, `Match`, `Started`, `admitted`, `seenRoster`, `privateRoom`, 파티 `route`의 조합이다. `generation`은 비동기 취소 토큰이다. 요청마다 번호를 기록하고 취소·시간 초과 때 올린다. 늦게 온 콜백은 번호가 다르면 무시하고, 이미 들어간 로비면 나온다.

## 6. 취소·퇴장·호스트 이탈

- 파티장 취소: generation 증가, 검색 중단, `route=idle`, 파티 입장 다시 허용, 경기 로비 나감.
- 파티원 취소(시작 전): 자기 `cancel`에 새 값 → 파티장이 보고 전체 취소. 시작한 경기에서는 자기만 나간다(아래 R60).
- 파티 구성 변경: 검색 시작 때와 명단이 다르면 취소(시작 전만).
- 파티장 교체: 매칭 취소 후 안내(시작 전만. 시작한 경기는 새 파티장과 그대로 계속).
- **시작 전** 호스트가 나갈 때: `phase=closed`, joinable=false를 먼저 게시한다. Steam이 로비 주인을 바꿔도 Host와 다르면 2초 뒤 대기실 종료(예약은 옮길 수 없다). → (R159부터) "나가기"는 예약을 `resv`에 적어 남은 1등에게 넘기고 나간다. 이 규칙(2초 뒤 종료)은 말없이 사라진 경우(크래시)에만 남았다([HOST §2](HOST.md)).
- (R503) **대기실이 닫혀도 공개 매칭 중인 파티는 다시 찾는다.** 혼자 있던 방장이 더 오래된 방으로 옮기거나 취소할 때 아직 자리를 다 받지 못한 파티가 있으면 방이 닫히고, 방장 크래시도 방을 닫는다. 예전에는 그 방의 다른 파티가 모두 "방장이 나가 경기가 끝났습니다"로 로비에 돌아갔다. 이제 파티장은 `RetryAdmission`으로 검색을 이어 가고, 파티원은 8초까지 파티장의 다음 방을 기다린다(파티원이 스스로 취소하면 `cancel`이 파티장의 검색까지 멈춘다). 비공개 방 · 번호로 들어간 방은 예전처럼 로비로.
- (R503) **방 번호로 들어간 방이 파티를 받지 못하면**(자리 없음, 시간 초과, 방이 닫힘) 이유를 보여 주고 로비로 돌아간다. 예전에는 그 방이 공개 방이면 파티의 모드로 공개 매칭을 시작했다. 봇이 있는 파티(출시 빌드)는 공개 방 번호로 들어가자마자 "봇이 있는 파티는 공개 매칭에…"로 돌아온다(예전엔 모든 공개 방장이 거절해 끝없이 다시 찾거나, 봇이 든 공개 방을 스스로 만들었다). 번호로 들어간 방에서 방장이 되어도 다른 방으로 합치러 가지 않는다.
- (R503) **대기실을 막 넘겨받은 방장**은 Steam이 방을 옮겨 주고 넘겨받은 예약(`resv`)을 읽은 뒤에야 시작 · 봇 추가 · 봇 빼기를 할 수 있다(`RunsRoom`, `CanStartGame`). 예전에는 그 사이에 '시작'을 누르면 방 쓰기가 모두 조용히 실패해 그 PC만 경기로 들어가고 나머지는 대기실에 갇혔다.
- (R503) **Steam 연결이 잠깐 끊기면 10초 기다린다.** 그동안 방을 읽지 않는다(Steam이 보여 주는 방이 낡아 방장 · 후계자가 그것으로 판단하면 안 된다). 10초가 넘으면 매칭 · 경기를 **한 번만** 나간다. 예전에는 끊기자마자 경기에서 나갔고, 끊긴 동안 0.25초마다 취소를 되풀이했다(파티원은 그때마다 `cancel`을 새로 씀).
- (R504) **다음 방장 차례인 PC도 멈춰 있으면**(게임 멈춤 · 아직 로딩 중 · 방장과 같은 공유기) 그다음 순번이 3초 뒤 `past`를 적고 이어받는다([HOST §5](HOST.md)). 예전에는 그 뒤의 멀쩡한 사람들이 있어도 10~12초 뒤 경기가 끝났다. 건너뛰어진 PC가 다시 움직이면 새 방장을 따라간다.
- (R504) **경기 끝(`EndMatch`)이 방 주인 이전 중에 사라지지 않는다.** 방장이 바뀐 직후에는 새 방장이 아직 방 주인이 아니라 `ended` 쓰기가 조용히 실패했고, 끝난 경기에 빈자리가 다시 열렸다. 이제 들고 있다가 주인이 되면 쓴다(`MatchEnded`는 그 사이에도 끝난 것으로 답한다).
- (R504) **이미 들어가 있는 파티의 초대를 받아들이면 아무 일도 없다.** 예전에는 파티를 나갔다가 같은 방에 다시 들어가, 파티장이면 파티장 자리를 잃었다(Steam이 주인을 다른 사람에게 넘김).
- (R295) **대기실에서 1등에게 넘기는 중에 받을 PC가 나가면**(그 파티가 취소 등) 넘긴 PC가 아직 방 주인일 때 `host`를 되돌리고 `resv`의 예약을 되살려 다시 방장을 맡는다(예전엔 2~10초 뒤 "방장이 나가" 방 끝). 받은 PC가 방 주인이 된 직후 나가면 아직 읽지 않은 `resv`를 읽은 뒤 자기 파티만 빼고 넘긴다(예전엔 빈 예약을 넘겨 남은 사람의 자리가 사라짐).
- **시작 후** 호스트가 나갈 때(나가기·게임 종료): 경기를 닫지 않고 가장 적합한 사람에게 방장과 로비 주인을 넘긴 뒤 나간다. 크래시·응답 없음은 `successors` 순서대로 후계자가 이어받는다. **로비 주인이 방장을 따라간다**(Steam이 아무에게나 넘긴 주인은 새 방장에게 다시 넘긴다) → [HOST](HOST.md).
- 시작 전에는 예약 그룹 단위 정리, 시작 후에는 로비에서 사라진 사람을 roster에서 뺀다. 그 자리는 **빈자리**가 되어 매칭 중인 사람이 채운다([§8](#8-경기-중-나간-사람과-돌아오기-r538-2026-11-10)).
- **(R60) 시작한 경기에서는 나간 사람만 나간다.** 파티원이든 파티장이든 방장이든, 경기가 시작된 뒤 나가거나 게임이 꺼지면 **그 사람만** 빠지고 나머지 파티원은 경기를 계속한다(그 자리는 빈자리로 채운다). 방장이 나가면 방장 이전([HOST](HOST.md)). 시작 전(대기실·검색 중)에는 예전처럼 파티가 함께 취소된다. 먼저 나온 파티원은 로비에서 "파티원들이 아직 경기 중입니다"를 보며 기다리고(파티 나가기로 혼자 할 수 있음), 파티장은 경기 중인 파티원이 돌아올 때까지 매칭을 시작할 수 없다(파티 멤버 데이터 `match`).
- 방장 신호 끊김(스냅샷 없음)은 [MOTION §4](MOTION.md)의 단계(0.5/2/12초)로 표시하고, 시작 후에는 4초에 방장 이전([HOST](HOST.md)). (R295) 경기 로딩 화면 동안은 재지 않고, 경기 씬에서는 그 씬의 링크가 방장의 첫 패킷이나 공동 시작 시각(`go`) 중 먼저 온 때부터 재서 `ReportHostSilence`로 넘긴다(폰 러쉬 포함).
- (R525) **대기실 움직임 패킷(`SteamMotion`, 채널 31)이 12초 끊겨도 대기실에서는 나가지 않는다.** 전에는 조용히 `Cancel`(오류 문구 없음) — 파티원이면 `cancel`을 써서 파티 매칭 전체가 취소됐다. 방장이 정말 사라진 대기실은 방 자체의 규칙(주인 · 방장 확인)이 끝낸다. 시작한 경기에서 이 스트림을 쓰는 장면(자체 시뮬레이션 없는 장면)만 예전처럼 나간다.
- (R525) **방장이 되는 PC는 방의 명단(`roster`)을 먼저 읽는다**(`ChangeHost`): 시작 순간 성능 1등 PC로 방장이 넘어가면 새 방장이 한 폴 전의 자기 명단을 게시해, 그 사이에 앉은 사람이 "예약이 해제되었거나 파티원 연결이 끊겼습니다"로 튕겼다.
- (R525) **나간 이유는 Player.log에**: 방을 만들고 · 들어가고 · 못 들어가고 · 나가고 · 다른 방으로 옮기고 · 방장이 바뀌고 · 방 주인을 기다리고 · 자리 예약이 풀릴 때마다 `[ChessFight] 세션: <무엇> | 방 <ID> · <phase> · 방장 · 주인 · 기록 방장 · 명단 · 방 인원 | t <초>` 한 줄, Steam P2P 세션 실패는 `[ChessFight] Steam P2P 연결 실패: <이름> · 이유 <번호> <설명>`. 전에는 `Fail`이 화면 글만 바꿔, 빌드 로그로는 왜 나갔는지 알 수 없었다.
- `SessionChanged` 이벤트 → `SteamMotion`이 연결·입력·예측 버퍼를 초기화한다. 경기 중 방장이 바뀌면 `HostChanged(이전, 다음)` → 캡슐·래그돌 쪽이 역할만 바꾼다(위치 유지). (R295) 폰 러쉬는 역할이 바뀌지 않은 PC도 `Host` 바뀜을 보고 받은 것을 지운다. 옛 방장과는 그 스트림 채널만 닫아 음성은 이어진다.

## 7. 공개 API 요약 (HUD가 쓰는 것)

**R48 소드파이트 더미 테스트:** 비공개 방장만 `AddTestBot(team)` / `RemoveTestBot(team)`로 원하는 팀에 한 명씩 추가·제거한다. `CanEditTestBots`, `CanAddTestBot(team)`, `TestBots(team)`은 버튼 권한·잔여 정원·추가 더미 수를 제공한다. 사람/파티 봇은 보존한다. `CanStartGame`을 HUD와 실제 시작 판정이 같이 써서 아직 예약 중일 때의 무응답 버튼을 막는다. 나+더미 1명으로 시작 가능, 공개 12명 규칙은 변경 없음. R48 당시에는 패킷 변경 없이 v7 유지했고 R49에서 v8로 변경했다. 당시 Core40·모의 세션20 통과. 09-27 사용자는 더미 기능이 잘 되고 혼자 테스트 가능하다고 확인했으며, 세부 정원/2PC는 별도 대기다.

## 8. 경기 중 나간 사람과 돌아오기 (R538, 2026-11-10)

사용자: "새로운 인원이 중도 난입되면 안 돼. 게임이 시작되면 그 방은 게임이 시작됐던 그 인원들로만 이루어져 있어야 해. … 나간 사람만 돌아올 수 있어야 하며 나간 시점의 구간의 체크포인트에서 시작되어야 해. 승리 조건은 플레이 중인 인원으로 실시간 조정되어야 해." R59 · R60의 **빈자리 채우기**(나간 자리를 매칭 중인 다른 사람으로, 출발 뒤 4분)를 대신한다([DECISIONS P47](../Project/DECISIONS.md)). 코드: 규칙 `Core/Starters.cs`(전 `Backfill.cs`), 물리 담당 쪽 `SteamSession.PublishSeats` · `SeatLate`, 돌아가는 쪽 `Rejoin` · `TrackRejoin`, 경기 장면 `SteamPawnRushLink`(체크포인트 · 기물), `CrownFinish`(승리 인원). **코드 · 모의 테스트 · Unity 사본만, 실제 Steam 확인 전.**

| 규칙 | 내용 |
|---|---|
| 누가 그 방의 사람인가 | 시작한 순간 자리에 앉아 있던 사람(봇 제외). 물리 담당 PC가 시작할 때 방 데이터 `starters`에 `id:팀:자리`로 적는다. 그 뒤로 바뀌지 않는다 |
| 새 사람 | **못 들어온다.** 시작한 방은 검색에 안 나오고(`open` 0), 방 번호로 Steam 방에 들어와도 자리 요청이 `full`로 거절된다(비공개 방도 같다) |
| 나간 사람 | 자리가 비고(팀은 한 명 적게 뛴다) 그 자리는 그 사람 것으로 남는다. 방은 그 사람이 다시 들어올 수 있게 Steam 입장만 열어 둔다(`joinable`) |
| 돌아오기 | 로비의 **"진행 중인 경기로 돌아가기"**(`CanRejoin` → `Rejoin()`): 방에 다시 들어가 자기 혼자의 자리 요청을 보내고(파티장이 아니어도), 물리 담당 PC가 `starters`의 **같은 팀 · 같은 자리**에 앉힌다. 로딩 화면(부제 끝 "· 경기로 복귀") 뒤 바로 경기 |
| 언제까지 | 경기가 끝나기 전(`ended` 전)이면 언제든. 시간 제한 없음(R60의 4분은 없어졌다). 방에 아무도 안 남으면 방이 사라져 끝 |
| 어느 경기인지 | 그 PC가 기억한다: 시작한 경기에 앉으면 방 번호를 `SaveRejoin`(PlayerPrefs `ChessFight.Rejoin.<SteamID>`)에 적고, 로비에서는 3초마다 Steam에 그 방을 물어(`RequestLobbyData`) 진행 중 · 안 끝남 · 내가 `starters`에 있음 · 같은 버전이면 버튼을 켠다. 끝났거나 사라졌으면 기록을 지운다. 그래서 **튕기거나 껐다 켠 게임도** 돌아간다 |
| 파티 | 돌아가는 것은 각자의 일이다. 파티 경로(`route`)를 읽지도 쓰지도 않는다: 파티장이 아니어도 되고, 파티장이 돌아가도 파티원이 끌려오지 않는다. 파티장이 파티를 다른 매칭에 넣은 동안에는 그 파티원의 버튼이 꺼진다 |
| 탈주 벌칙(§11) | 스스로 나간 기록은 돌아와도 남는다. 매칭 정지 중이어도 돌아가기는 된다(매칭이 아니므로) |
| 어디서 다시 시작하나 | 폰 러쉬: **나갈 때 마지막으로 지난 체크포인트의 되살아나는 자리**, 그때의 기물로(아래). 소드 파이트: 폰으로(그 모드의 '늦게 들어온 사람' 규칙) |
| 승리 인원 | 폰 러쉬: 지금 경기에 있는 우리 팀 플레이어의 과반(6명 4 · 5명 3 · 4명 3 · 3명 2 · 2명 2 · 1명 1). 나가면 줄고 돌아오면 원래대로([UI §17](../Architecture/UI.md)) |
| 알림 | 경기 중 상태 줄 "경기 중 · n명이 자리를 비움 · 경기가 끝나기 전에 돌아올 수 있습니다", 누가 돌아오면 6초 "○○ 님이 경기에 돌아왔습니다" |

```text
[시작]          물리 담당: seats=3,3 · starters=A:0:0;B:0:1;… · free=0,0 · open=0 · 방 잠금(joinable=false)
[B가 나감]       물리 담당: roster에서 뺌 → B팀 free=1 · open은 그대로 0 · 방 입장만 엶(joinable=true)
                B의 PC: 방 번호를 기억한 채 로비로 → 3초마다 그 방을 물음 → "진행 중인 경기로 돌아가기"
[C가 매칭]       검색에 그 방이 없음 → 다른 대기실 또는 새 방 (방 번호로 들어와 요청해도 full)
[B가 버튼]       입장 → reserve 채팅(members = [B]) → 물리 담당: starters의 B 자리에 앉힘 · grant=ok · roster 갱신 → free=0 · 방 잠금
[경기 끝]        ended=1 → 방 잠금, 아무도 못 돌아옴. 로비의 버튼도 사라짐
```

- **자리 요청 검사**(`SeatLate`): 보낸 사람이 `starters`에 있고, 요청 명단이 자기 혼자이고, 경기가 안 끝났을 때만. 낯선 사람, 시작 멤버를 끼워 넣은 가짜 파티, 다른 사람을 데려온 시작 멤버는 모두 `full`. 같은 요청을 또 보내면 `ok`만 다시 답한다.
- **물리 담당이 바뀌어도** `starters`는 방에 있어 새 물리 담당이 같은 사람을 같은 자리로 받는다(규칙 15, [HOST](HOST.md)). 물리 담당이던 PC가 튕겼다 돌아오면 R536 규칙대로 로딩 5초 뒤 다시 물리 담당이 될 수 있다(10% 이상 좋을 때).
- **폰 러쉬의 체크포인트 · 기물**(`SteamPawnRushLink`): 플레이어가 명단에서 빠지면 모든 PC가 그 **자리**(팀 · 번호)의 마지막 체크포인트(`Checkpoint.Order`)와 기물을 적어 둔다(`away`). 돌아와 그 자리에 다시 생길 때 출발 칸 대신 그 체크포인트의 자리(`CourseCheckpoint.SpotWorld(자리 번호)`)에 세우고 기물을 입힌다. 체크포인트는 원래 PC마다 자기 물리로 알아내는 값이라(R502) 자리를 비웠던 PC는 모른다 → 물리 담당이 코스 상태(CFP6)에 **자리별 체크포인트 · 기물**을 싣는다(뛰는 자리와 비운 자리 모두; 값이 바뀌면 3번 연달아, 그 밖에는 15번에 한 번). 받은 PC는 더 앞선 체크포인트면 받아들이고, 비운 자리 것은 적어 둔다([PITFALLS 80](../Environment/PITFALLS.md), [PAWN_RUSH_SECTIONS](../PawnRush/PAWN_RUSH_SECTIONS.md)).
- **한계:** 어느 경기였는지는 그 PC의 PlayerPrefs에만 있다(다른 PC에서 로그인하면 버튼이 없다). 방에 Steam 입장을 열어 두는 동안 방 번호를 아는 사람이 방에 들어와 있을 수는 있다(자리는 못 받는다). 체력 · 스킬 쿨다운 · 들고 있던 물건은 돌아올 때 이어지지 않는다. 소드 파이트는 고른 기물을 잃고 폰으로 온다.

## 9. 채팅 (R61, 2026-09-30)

승규 님 요청: 파티·전체·팀 채팅, 보낸 사람은 **Steam 이름**. 채팅 서버는 없다. 이미 쓰는 **Steam 로비 채팅**(`SendLobbyChatMsg`)으로 보낸다. 화면은 [UI §9](../Architecture/UI.md#9-채팅-r61-2026-09-30).

| 채널 | 보내는 곳 | 받는 사람 | 쓸 수 있을 때(`CanChat`) |
|---|---|---|---|
| 파티 | 파티 로비 | 파티원 모두(로비에서도, 경기 중에도) | 파티가 있으면 늘 |
| 전체 | 경기 방 | 방의 모두(대기실이면 대기실 인원, 경기면 12명) | 경기 방에 있을 때(검색 중 들른 대기실 포함) |
| 팀 | 경기 방 | 방의 모두가 **받지만** 같은 팀 화면에만 보인다 | 경기 방에서 명단에 내 자리가 있을 때 |

- **글의 모양**(`Core/Chat.cs` `ChatText`): `CFC1|p|글`(파티), `CFC1|a|글`(전체), `CFC1|0|글`·`CFC1|1|글`(백팀·흑팀). 경기 방 채팅에는 자리 요청 JSON(`{"kind":"reserve",…}`, §4·§8)도 흐르는데, 앞의 `CFC1|`로 구분한다. 채팅 줄은 방장의 자리 요청 처리로 가지 않고, 자리 요청은 채팅 창에 나오지 않는다.
- **받는 쪽 검사**(`SteamSession.Hear`): 그 로비의 멤버가 보낸 것만. 파티 줄은 파티 로비로 온 것만, 경기 줄은 경기 방으로 온 것만. 팀 줄은 **내 팀과 같고, 보낸 사람도 명단에서 그 팀일 때만**(다른 팀 사람이 팀 번호를 속여 보내도 안 보인다). 글은 다시 `Clean`(80자, 줄바꿈·제어·보이지 않는 서식 문자 제거).
- **보내는 쪽 규칙**(`Say`): 빈 글은 안 보냄, 1초에 한 줄(`ChatThrottle`), 80자. 막히면 이유 문장을 돌려주고 화면이 3초 보여 준다. 자기 줄도 Steam이 되돌려 준 것을 받아 로그에 넣는다(실제로 전달된 것만 보인다).
- **이름**: 받은 순간의 `Name(보낸 사람)` = `SteamFriends.GetFriendPersonaName`(로비 오른쪽 위에 보이는 그 이름). 봇은 말하지 않는다.
- **로그**(`ChatLog`, `SteamSession.Chat`): 채널마다 최근 50줄, 채널마다 1부터 번호, 채널별 안 읽은 수. **다른 파티로 옮기면 파티 채널을, 다른 경기 방으로 옮기면(검색 중 방을 옮기는 것 포함) 전체·팀 채널을 비운다.**
- **알림 줄**: 파티 채널 "○○ 님이 파티에 들어왔어요 / 나갔어요", 시작한 경기의 전체 채널 "○○ 님이 경기를 나갔어요 / 빈자리에 들어왔어요"(§8). 들어가는 순간 이미 있던 사람은 알리지 않는다.
- **프로토콜은 v14 그대로.** 채팅을 모르는 빌드는 `CFC1|` 줄을 JSON으로 읽다 실패해 버릴 뿐이라 매칭·자리 요청에 해가 없다(그 빌드의 사람에게는 채팅이 안 보일 뿐). 그래도 같은 빌드끼리만 만나는 규칙(K5)은 그대로다.
- **알고 있는 한계**: 팀 줄은 상대 팀 PC에도 도착한다(화면에만 안 보임). 고친 클라이언트는 읽을 수 있다. 막으려면 팀원에게만 P2P로 보내야 한다(나중 일). 받는 쪽 도배 제한도 없다(보내는 쪽 1초 제한만).
- 공개 API: `Chat`(로그), `CanChat(channel)`, `Say(channel, text)` → ""(보냄 또는 보낼 것 없음) 또는 막힌 이유.

## 10. 방장과 물리 담당, 양도와 강퇴 (R533, 2026-11-10)

사용자 매칭 규칙 4번: "(지금 상태가 나은지 이 제안이 나은지 판단 후) 게임 시작, 강퇴 권한 등 게임 관리 권한이 있는 방장 PC와 제일 좋은 PC로서 물리연산을 담당하는 PC를 구분해서 선정한다. 관리 권한의 방장 PC는 해당 유저가 방장을 양도하거나 방을 나가면 다른 플레이어에게 이전된다. 물리 담당 PC는 방장 권한과는 별개로 방에 존재하는 유저에 변동이 있을 때마다 제일 좋은 PC(CPU, GPU 통합)가 물리 담당 PC가 된다. 물리 담당 PC도 마찬가지로 게임 중, 매칭 중 등 방에서 나가면 다음으로 좋은 PC를 보유한 유저에게 자동 이전 된다." → 판단: 제안이 낫다. 이유와 다르게 한 두 가지는 [DECISIONS P44](../Project/DECISIONS.md)(그중 '경기 중에는 물리 담당을 그대로'는 R536에서 사용자 결정 "바로 넘기기"로 바뀌었다: P46).

| | 방장(관리) | 물리 담당 PC |
|---|---|---|
| 코드 | `SteamSession.Manager` · `IsManager`, 방 데이터 `manager` | `Host` · `IsHost`, 방 데이터 `host`, Steam 방 주인 |
| 누가 | 방을 만든 사람 → 양도받은 사람 → 나가면 남은 사람 중 자리 번호가 가장 앞선 사람(같으면 백팀, 그다음 Steam ID). 봇은 안 된다 | 성능 점수 1등([HOST §3](HOST.md): CPU 벤치마크 × 그래픽 계수 × 코어 · 메모리, 핑 반영) |
| 하는 일 | 게임 시작, 대기실 강퇴, 방장 양도, (개발 빌드 · 비공개 방) 봇 넣기 · 빼기 | 모든 캐릭터 계산, 방 데이터 쓰기, 자리 예약 장부, 빈자리 채우기 |
| 바뀔 때 | 양도. 방장이 방에서 나감 · 튕김 · 자리를 잃음 | 대기실: 사람이 드나들 때마다 다시 고름(R159 · R294). 경기 중: 그 PC가 나가거나 응답이 없거나 계속 느릴 때([HOST §5](HOST.md)), 그리고 **(R536) 사람이 드나들 때마다 1등이 10% 이상 좋으면**([HOST §2](HOST.md), P46 — R533의 '들어온 것만으로는 넘기지 않는다'를 사용자 결정으로 바꿈) |
| 화면 | 입장 화면 카드의 이름 아래 "방장", 경기 명단 "· 방장", 알림 "방장이 ○○ 님으로 바뀌었습니다" | 카드의 이름 아래 "물리 담당", 경기 명단 "· 물리 담당", F3 칩 "물리 담당", 알림 "물리 담당 PC가 ○○ 님으로 바뀌었어요" |

- **방 데이터는 Steam 방 주인만 쓸 수 있고 주인은 물리 담당 PC다.** 그래서 방장이 물리 담당이 아니면 방장의 일은 자리 예약(§4)처럼 **방 채팅 요청**으로 간다: `{"kind":"manage","op":"start|give|kick|fill|addbot|clearbots|addtest|removetest","target":<Steam ID>,"team":0|1,"seq":n}`. 물리 담당 PC는 **방 데이터의 `manager`가 보낸 것만**, 번호(`seq`)마다 한 번만 실행한다(`Manage`). 방장이 곧 물리 담당 PC면 요청 없이 바로 한다.
- **요청은 될 때까지 다시 보낸다**(`Ask` · `SendAsk`, 1초마다): 시작은 12초 동안, 나머지는 2.5초 동안. 물리 담당 PC가 막 바뀌어 아직 방 주인이 아니거나 넘겨받은 예약을 읽기 전이면, 또는 들어온 사람이 자리를 받는 중이면 그 요청은 실행하지 않고 두었다가 다음에 온 같은 번호를 실행한다 — 물리 담당이 바뀌는 순간에 '게임 시작'을 눌러도 사라지지 않는다. 같은 일을 또 누르면 새 요청이 아니라 보내는 시간만 늘어난다(봇 한 명 추가만 누른 만큼).
- **방장 화면이 읽는 값은 방 데이터**: 인원 = 6 − `free0` · `free1`, 자리를 받는 중인 사람 = `seating`, 더미 수 = 명단. 자리 예약 장부(`reservations`)는 물리 담당 PC에만 있다([PITFALLS 79](../Environment/PITFALLS.md)). `CanStartGame`은 방장에게만 참이고(`SeesRoomReady`), 물리 담당 PC가 요청을 받으면 자기 장부로 다시 본다(`HostCanStart`).
- **방장 이어받기**: 물리 담당 PC가 폴링마다 `manager`가 방에 있고 자리가 있는지 본다(`KeepManager`). 없으면 다음 사람(`NextManager`)을 쓴다. 방장이 스스로 나갈 때 자기가 방 주인이면 나가면서 쓴다(`LeaveManagerBehind`). 모든 PC는 `FollowManager`로 읽고, 바뀌면 6초 알림("방장이 ○○ 님으로 바뀌었습니다." / "이 PC가 방장이 되었습니다. 게임 시작과 방 관리를 맡아요.")과 로그 `방장(관리) 바뀜`.
- **양도**(`GiveManager`): 방에 앉아 있는 사람에게. 입장 화면 카드의 [양도] → 금색 "확인" → 3초 안에 한 번 더([UI §17](../Architecture/UI.md)).
- **강퇴**(`Kick`): **시작 전 대기실에서만.** 그 사람이 함께 온 파티(자리 예약 묶음)를 통째로 내보내고 `kicked`에 적는다: 그 방의 자리 요청이 거절되고(방 번호로 들어와도), 매칭 검색은 그 방을 건너뛰어 다른 방이나 새 방으로 간다. 내보내진 PC는 `kicked`에서 자기를 보고 방을 나가 "방장이 방에서 내보냈습니다."를 띄운다(파티원도 각자). 방장 자기 파티와 봇은 대상이 아니다(파티원은 파티에서 내보내고, 봇은 봇 버튼으로). 물리 담당 PC도 내보낼 수 있다(그 PC가 다음 PC에 방을 넘기고 나간다). 경기 중 강퇴는 없다 — 방장이 상대 팀을 내보낼 수 있어서.
- **한계**: 물리 담당 PC가 고친 클라이언트면 방장의 요청을 무시할 수 있다(전에도 그 PC가 방장이었으니 새 위험은 아니다). `kicked`는 그 방만 막는다(다음에 생긴 방에서는 다시 만날 수 있다). 방장이 말없이 사라지면(크래시) 물리 담당 PC가 다음 폴링에서 다음 방장을 정한다. 물리 담당 PC가 말없이 사라진 **대기실**은 방장이 남아 있어도 예전 규칙대로 끝난다([HOST §8](HOST.md)).
- 모의 테스트(`SessionFlowTests`): `The room's manager (rule 4)…`, `A manager on another PC sees the players still being seated…`, `The manager puts a player out of the waiting room…`, `A manager that crashes…`, 그리고 '시작은 방장이'로 고친 기존 9개(물리 담당이 바뀌는 중에 누른 시작이 방 주인이 된 뒤 실행되는 46번 포함).

## 11. 탈주 벌칙 (R533, 2026-11-10)

사용자 매칭 규칙 3번: "탈주를 한 플레이어는 2번 까지 기회가 있으며 3번 부터 매칭 10분 정지 4번 30분 정지 5번 1시간 정지이며 24시간이 지나면 초기화 된다(빌드용, 에디터는 미적용)". 규칙은 `Core/LeavePenalty.cs`(순수 C#), 세고 막는 것은 `SteamSession`, 저장과 켜기는 `NetworkRuntime`. 무엇을 탈주로 볼지의 결정과 이유는 [DECISIONS P45](../Project/DECISIONS.md).

| | |
|---|---|
| 탈주로 세는 것 | **시작한 공개 경기**를 **끝나기 전에 스스로** 나감: Esc 메뉴의 게임 나가기(`LeaveByChoice`), 경기 중 게임 종료(창 닫기 · Alt+F4 → `Dispose`). 그때 내가 자리에 앉아 있고 다른 사람이 아직 그 경기에 있어야 한다(`WouldDesert`) |
| 세지 않는 것 | 끝난 경기(방의 `ended`, 또는 이 PC가 결과를 본 뒤 `SawResult`), 비공개 방, 시작 전 대기실(매칭 취소), 연결 끊김 · 오류 · 물리 담당 PC가 사라져 나가짐(`Abort` · `Fail` · 링크가 부른 `Cancel`), 강제 종료 · 크래시, 자리를 받기 전, 사람이 나뿐인 경기, Unity 에디터 |
| 횟수 | 탈주마다 일어난 때부터 24시간 동안 센다(`LeavePenalty.Window`, 굴러가는 24시간). 최근 16개까지 기억 |

| 정지 중 막는 것 | 공개 매칭(`FindMatch`), 방 번호로 공개 방에 들어가기. 비공개 방(테스트 · 친구 방)은 된다. 파티원이 정지 중이면 파티장의 공개 매칭도 막힌다(파티 멤버 데이터 `ban`) |
| 시계 | Steam 서버 시각(`ServerNow`) — PC 시계를 돌려도 그대로 |
| 저장 | PlayerPrefs `ChessFight.Leaves.<SteamID>`(탈주 시각 목록 `t,t,…`). 서버가 없어 이 PC에만 있다 |
| 켜는 곳 | `NetworkRuntime`: `Session.LeavePenaltyOn = !Application.isEditor`. 꺼져 있으면 세지도 막지도 않는다 |

Esc 메뉴의 나가기 경고 첫 줄(`LeaveWarning` → `GameMenu.OnlineCost`) "지금 나가면 탈주 n회로 기록됩니다. 24시간 안에 3회부터 매칭이 정지됩니다." / "지금 나가면 24시간 안의 3번째 탈주라 매칭이 10분 동안 정지됩니다." 나간 뒤 로비의 오류 줄 "경기 도중 나가 탈주 n회로 기록됐어요…" / "…탈주 3회째예요. 매칭이 10분 동안 정지됩니다."
