# 방장 판정 방식: 점검, 다듬을 것, 3인 시험 (R117, 10-10)

> 승규 님: "지금 방장 컴퓨터에서 계산을 하는데 이러면 우려점 있어? 더 좋은 방안이나 좋은 점도 말해줘" → "지금 방식에서 더 다듬어야 할 사항 있어?" → "이거 문서로 자세하게 뽑아줘. 오늘 3인 테스트 해볼 건데 수치 알려줄게."
>
> 범위: `skill-network-test` 브랜치의 스킬 시험 씬 온라인(폰 러쉬·퀸 오브 더 힐). 소드 파이트 스킬은 아직 오프라인.
> 이 문서의 수치는 **코드에서 읽은 값과 계산값**이다. Steam 3인 시험은 이번이 처음이고, **사람이 본 것은 아직 없다.**
> 관련 문서: [SKILLS_ONLINE](SKILLS_ONLINE.md)(스킬 온라인 구현, §14 시험 화면), [HOST](HOST.md)(방장 선정·이전), [VALIDATION](VALIDATION.md)(확인 기록).

## 0. 한눈에

- 지금 방식은 **방장 판정**이다. 방장 PC 하나가 물리와 스킬을 모두 계산하고, 참가자는 입력을 보내고 결과를 받아 그린다. 랙돌 물리 게임에는 이 방식이 맞다. **바꾸지 않고 다듬는다**(§4).
- 큰 우려는 셋이다.
  - 방장만 유리하다(입력 지연 0).
  - 방장 PC와 회선이 모두의 품질을 정한다.
  - 인원이 늘면 방장이 올리는 양이 빨리 는다(12명이면 약 2.1 Mbps, R297 전 2.4).
- 다듬을 것은 9가지다(§7). 무엇부터 할지는 **오늘 3인 시험 수치로 정한다**(§9).
- **정정:** 이전 답에서 "방장 자동 고르기"를 새로 할 일처럼 말했는데, **이미 있다.** PC 성능과 Steam 핑으로 시작할 때 고르고, 방장이 느려지면 넘기고, 방장이 나가면 다음 사람이 이어받는다(§1.3). 남은 일은 시험으로 확인하는 것이다.
- **오늘 할 일:** §8 순서대로 시험 1~6을 한다(약 70분). 시험마다 각 PC 오른쪽 위 수치를 **캡처해서 보내거나**, §8.5 양식으로 적어 보낸다.

## 1. 지금 방식

### 1.1 흐름

```
참가자 PC                                   방장 PC
 입력 40바이트 (초당 60번 + 바뀌면 바로, 최대 120번) ──→  물리 초당 120번 · 스킬 판정
                                         ←──  스냅샷 (30 + 말 수 × 65바이트, 갈고리를 돌리거나 던진 말은 72, 초당 30번 · 6명까지 60번, R306)
                                         ←──  스킬 패킷 (참가자마다, 스냅샷마다, 1024바이트 안)
 화면: 스냅샷을 70~160 ms 늦게 이어 그림(흔들림 완충)
```

| 무엇 | 누가 → 누구 | 크기 | 얼마나 자주 | 안에 든 것 |
|---|---|---|---|---|
| 입력 | 참가자 → 방장 | 40바이트 | 초당 60번 예약표 + 바뀐 프레임에 바로(누름 · 놓음 · 움직이기 시작 · 멈춤 · 20° 넘게 꺾음), 1/120초 안에 두 번은 안 보냄(R306) | 버튼, 이동, 조준 방향, 누른 횟수, 받은 신호 번호, 이 PC가 잰 왕복·재생 지연·손실(`CFR8`) |
| 스냅샷 | 방장 → 참가자마다 | 30 + 65 × 말 수, 갈고리를 돌리거나 던진 말마다 +7 (3명 225, 12명 810~894). R297 전에는 74 × 말 수(252 · 918) | 초당 30번, 스냅샷만으로 방장 올림이 128 KB/초 안이면 60번(6명까지, 사람 2~3명 + 봇 12명, R306). 폰 러쉬 코스 상태는 늘 30번 | 말마다 자세·상태 |
| 스킬 패킷 | 방장 → 참가자마다 | 23 + 스킬 중인 말 29씩 + 밧줄 18 + 바리케이드 3 + 순간 신호 28씩 | 스냅샷마다 | 쿨타임·예고·조준, 밧줄, 바리케이드, 아직 확인 안 된 순간 신호 |
| 경기 상태(퀸 오브 더 힐) | 방장 → 모두 | 400자 안 | 초당 2번 | 열린 구간 |

모든 패킷은 "안 와도 다시 안 보내는" 방식(Steam Unreliable)이다. 꼭 가야 하는 것은 이렇게 지킨다.
- **누름:** "누른 횟수"를 보낸다. 패킷 하나가 빠져도 다음 패킷에 횟수가 남는다.
- **순간 신호(맞음·폭발·착지):** 참가자가 "여기까지 받음"을 보낼 때까지 스냅샷마다 다시 싣는다.

### 1.2 화면에 그리는 법 (자세히는 [SKILLS_ONLINE §9](SKILLS_ONLINE.md#9-r111-화면에-그리는-법))

| 무엇 | 언제 그리나 |
|---|---|
| 몸 | 방장 스냅샷을 재생 지연(70~160 ms)만큼 늦게 이어 그림 |
| 상대 예고·조준·쿨타임 | 도착하자마자 |
| 맞음·폭발·착지 | 몸과 같은 박자(재생 지연만큼 늦게) |
| 내 누름 | 누르는 순간 내 화면에 예고를 먼저 그림(미리 그림). 방장 답이 안 오면 되돌림 |
| 히트스톱 | 각자 화면에서 그 말들의 그림만 잠깐 멈춤. 방장 물리는 멈추지 않음 |
| 소리 | 순간 신호와 스킬 단계로 남. 참가자도 같은 순간에 들음(재생 지연만큼 늦게) |

### 1.3 방장 고르기와 이어받기 — 이미 있음 ([HOST](HOST.md), `HostElection`·`SteamSession`)

| 언제 | 어떻게 | 화면 메시지 |
|---|---|---|
| **시작**을 누를 때 | 모두의 PC 성능 점수(CPU 시험·코어·메모리·프레임)와 다른 사람까지의 평균 핑(Steam 추정)으로 순위를 매긴다. 평균 핑이 60 ms를 넘으면 점수를 깎는다. 방 만든 사람보다 **1.15배 이상** 좋은 PC가 있으면 그 PC가 방장이 된다 | "성능이 더 좋은 ○○ 님의 PC가 방장을 맡습니다." |
| 경기 중 방장이 느릴 때 | 방장 프레임 평균이 40 ms(25 fps 아래)인 채로 **5초** 넘게 가면, PC 성능이 **1.5배 이상**인 사람에게 넘긴다. 넘긴 뒤 45초 동안은 다시 넘기지 않는다 | "방장 PC가 느려져 ○○ 님이 방장을 이어받습니다." |
| 방장이 게임을 끄거나 "경기 나가기" | 방장이 2초마다 적어 둔 "다음 방장 순서"대로 바로 이어받는다 | — |
| 방장이 방에는 있는데 소식이 없을 때(인터넷 끊김) | **4초** 뒤 다음 사람이 이어받는다. 시작·교체 직후 10초는 빼고 센다(씬 로딩 멈춤과 구별) | "방장 연결이 끊겨 이 PC가 방장을 이어받았습니다." |
| 이어받을 때 스킬 | 쿨타임·진군·기상 보호·호위, 비숍 밧줄, 바리케이드를 이어받는다. **하던 스킬은 취소되고 쿨타임으로 넘어간다**(D-S6) | — |
| 12초 넘게 아무 소식이 없을 때 | 참가자는 경기를 나간다 | "호스트가 자세 전송을 멈췄어요. 경기를 나갑니다." |

> **주의: "테스트 방 만들기"를 누른 PC가 방장이 아닐 수 있다.** 오른쪽 위 수치 상자 맨 윗줄이 "네트워크 · **방장**"인지 "네트워크 · **참가자**"인지로 확인한다.

## 2. 좋은 점

| 좋은 점 | 왜 |
|---|---|
| 화면이 서로 어긋나지 않음 | 판정하는 곳이 한 곳뿐이다. 랙돌 물리는 PC마다 계산 결과가 조금씩 달라서 각자 계산하면 금방 어긋난다. R110 두 PC 시험에서 어긋남이 없었던 이유다 |
| 서버 비용 0 | Steam이 연결을 이어 준다(중계 포함) |
| 만들고 고치기 쉬움 | 스킬 규칙이 방장 코드 한 곳에만 있다. 새 스킬도 "상태 칸 + 순간 신호"만 붙이면 온라인이 된다 |
| 참가자 치트에 강함 | 참가자는 입력만 보낸다. 쿨타임·맞음은 방장이 정한다 |
| 늦게 들어와도 바로 보임 | 방장이 매번 전체 상태(밧줄·바리케이드 포함)를 보낸다 |
| 나중에 전용 서버로 옮기기 쉬움 | 판정 코드(`LabNetLink`)와 연결 코드(`SteamRagdollLink`·`LoopbackLabLink`)가 이미 나뉘어 있다 |

| W3 | **방장 회선(올림)** | 방장은 참가자 수만큼 스냅샷을 보내고, 스냅샷도 인원만큼 커진다. 인원의 제곱에 가깝게 는다 | 스냅샷을 작게 만듦(말 하나 65바이트, R297에서 74 → 65) | 12명이면 약 261 KB/s(약 2.1 Mbps, R297 전 약 296 KB/s). 집 와이파이나 휴대폰 테더링이면 위험(§6) | 방장 "보내기 KB/s", 참가자 "손실" |
| W4 | **방장까지 거리** | 모든 참가자의 지연이 "나 ↔ 방장" 거리로 정해진다 | 시작할 때 핑을 점수에 넣음 | Steam이 추정한 핑이라 실제와 다를 수 있다(§7 P8) | 방장 화면 참가자 줄의 "왕복" |
| W5 | **방장이 나감** | 판정하던 곳이 사라진다 | 다음 방장이 바로(끊김이면 4초 뒤) 이어받음 | **사람이 본 적 없음.** PC 한 대 로컬 시험에는 방장 이전이 없다(§7 P7) | 시험 5 |
| W6 | 방장 치트 | 방장은 결과를 마음대로 바꿀 수 있다 | 없음 | 친구끼리는 괜찮다. 순위전이 생기면 문제 | — |
| W7 | **스냅샷 크기 한도** | 한 패킷은 1024바이트까지 | 12명 810바이트, 모두 갈고리를 돌리거나 던져도 894바이트로 안에 든다(R297 전 918) | 남은 자리는 130바이트: 말마다 11바이트가 늘면 모두 갈고리를 돌리거나 던진 12명에서 넘친다(§7 P6) | 스냅샷 바이트(3명이면 225, 갈고리를 돌리거나 던진 말마다 +7) |

## 4. 다른 방식과 비교

| 방식 | 어떻게 | 좋은 점 | 나쁜 점 | 이 게임에 |
|---|---|---|---|---|
| **방장 판정 (지금)** | 플레이어 PC 하나가 판정 | 서버 비용 0, 어긋남 없음, 만들기 쉬움 | 방장 유리, 방장 PC·회선에 달림 | **맞음. 유지하고 다듬기** |
| 전용 서버 | 회사 서버가 같은 판정 코드를 돌림 | 공평, 방장 나감 없음, 치트에 강함 | 서버 비용·운영, 서버까지 거리 | 순위전이나 공개 매칭이 커질 때. 구조가 같아서 나중에 옮기기 쉬움 |
| 각자 계산 (같은 계산 맞추기·롤백) | 모두가 같은 입력으로 같은 계산 | 지연이 거의 안 느껴짐(격투 게임 방식) | 모든 PC의 계산 결과가 완전히 같아야 함 | **안 맞음.** Unity 물리는 PC마다 결과가 조금씩 다름 |
| 나눠 판정 (내 말은 내 PC가) | 자기 말은 자기 PC가 계산 | 내 조작이 즉시 | 부딪힘·잡기·넘어짐을 누가 정하는지 다툼, 치트에 약함 | 랙돌끼리 부딪히는 게임이라 어울리지 않음 |

## 5. 지연은 어디서 생기나

참가자가 누르고 → 방장이 판정하고 → 내 화면에 보이기까지(평균, **계산값**). 방장 · 참가자 모두 60 fps, 물리 초당 120번일 때다.

(R306, 11-03) **다시 계산했다.** R117 표("지금 왕복 + 약 100 ms")는 두 곳을 작게 잡았다. ① 방장 물리 차례 "약 4 ms": 방장은 입력을 Update에서 읽어 **다음 프레임의** 물리에 넣었다. 도착부터 평균 1.5프레임(약 25 ms)이다. ② 폰 러쉬 스냅샷 "초당 30번": "마지막으로 보낸 뒤 1/30초"로 보내 60 fps에서 다음 프레임으로 미끄러져, 실제로는 초당 약 20~25번이었다(소드 파이트 · 랩은 예약표라 30번). R306로 바꾼 항목은 오른쪽 끝 칸이다. 이 PC 한 대에서 잰 값은 §11.

| 구간 | R306 전 | R306 뒤, 7명 이상 (초당 30번) | R306 뒤, 6명 이하 (초당 60번) | 항목 |
|---|---|---|---|---|
| 입력이 보내지길 기다림 | 0~17 ms (평균 약 6) | 0 (누른 프레임에 바로) | 0 | [2] |
| 방장까지 | 왕복의 절반 | 같음 | 같음 | (직접 연결 · ICE는 안 바꿈) |
| 방장 물리 차례 | 약 25 ms | 약 8 ms (그 프레임 첫 물리 단계에서 읽음) | 약 8 ms | [3] |
| 스냅샷이 보내지길 기다림 | 약 12 ms (폰 러쉬 실제 초당 20~25번), 소드 파이트 약 8 ms | 약 8 ms (두 프레임에 한 번) | 0 (프레임마다) | [1] [5] |
| 내 PC까지 + 읽을 프레임 | 왕복의 절반 + 약 8 ms | 같음 | 같음 | |
| **화면의 "누름 → 방장 반응"** | **왕복 + 약 50 ms** | **왕복 + 약 25 ms** | **왕복 + 약 17 ms** | |
| 재생 지연(흔들림 완충) | 70 ms (손실 · 흔들림이 있으면 160까지) | 같음 | 약 37 ms (바닥 = 간격 × 2 + 4) | [5] |
| **내 몸이 움직여 보이기까지** | **왕복 + 약 120 ms** | **왕복 + 약 95 ms** | **왕복 + 약 55 ms** | |
| 같은 것, 폰 러쉬 F7 "내 폰 먼저"(기본 꺼짐) | — | 왕복 + 약 62 ms | 왕복 + 약 38 ms | [6] |
| **내 예고 · 조준(미리 그림)** | **0 ms** (누르는 순간) | 같음 | 같음 | |

| 왕복 지연 | 40 ms | 100 ms | 200 ms | 300 ms |
|---|---|---|---|---|
| 내 몸이 움직여 보이기까지, R306 전 | 약 0.16초 | 약 0.22초 | 약 0.32초 | 약 0.42초 |

- 화면의 두 숫자(F3 상자)는 R306부터 따로 잰다: "누름 → 방장 반응"은 누른 입력의 보낸 시각이 처음 되돌아온 스냅샷이 도착할 때까지, "내 몸이 움직여 보이기까지"는 그 스냅샷의 방장 시각을 내 폰에 그리는 프레임까지다(Core `PressTimer`). 받은 보낸 시각은 R306부터 "물리에 적용한 입력"이라 방장 물리 차례가 두 숫자와 왕복 지연에 모두 들어간다.

- 모든 열에 같게 더해지는 것: 그래픽 카드가 쌓아 두는 프레임(PC 기본 2, 약 17~33 ms)과 모니터. `-queuedFrames=1`로 1을 시험할 수 있다(개발 빌드, [4], §11).

## 6. 방장이 올리는 양 (계산)

방장 보내기 ≈ 스냅샷(30 + 65 × N바이트, 갈고리를 돌리거나 던진 말마다 +7) × 초당 30번 × (N − 1)명 + 스킬 패킷. (R297, 11-02: 말 하나 74 → 65바이트. 괄호 안은 R297 전 값이다.)

| 인원 N | 스냅샷 한 개 | 방장 보내기 (30번) | 방장 보내기 (60번) | 참가자 받기 (30번) |
|---|---|---|---|---|
| 2 | 160바이트 (178) | 4.7 KB/s (5.2) | 9.4 KB/s (10.4) | 4.7 KB/s (5.2) |
| **3** | **225바이트** (252) | **13.2 KB/s** (14.8) | 26.4 KB/s (29.5) | **6.6 KB/s** (7.4) |
| 4 | 290바이트 (326) | 25.5 KB/s (28.7) | 51.0 KB/s (57.3) | 8.5 KB/s (9.6) |
| 6 | 420바이트 (474) | 61.5 KB/s (69.4) | 123.0 KB/s (138.9) | 12.3 KB/s (13.9) |
| 8 | 550바이트 (622) | 112.8 KB/s (127.6) | 225.6 KB/s (255.1) | 16.1 KB/s (18.2) |
| 12 | 810바이트 (918) | 261.0 KB/s, 약 2.1 Mbps (295.8) | 522.1 KB/s, 약 4.3 Mbps (591.7) | 23.7 KB/s (26.9) |

- KB는 1024바이트다(시험 화면과 같은 단위). 스킬 패킷은 빼고 계산했다. 스킬 패킷은 참가자마다 초당 약 1~4 KB 더 든다(스킬을 많이 쓸수록 큼).
- 갈고리를 돌리거나 던진(돌리기 · 날아감 · 당김 · 박힘) 말은 7바이트 더 크다. 12명이 모두 그러면 894바이트, 방장 보내기 288.1 KB/s다.
- **계산이 맞는지:** R110 두 PC 시험에서 승규 님이 본 방장 보내기 5.2~5.4 KB/s, 폰 하나에 74바이트는 위 표 N = 2 줄의 괄호 값(R297 전)과 같다. R297 뒤 값은 아직 아무도 재지 않았다([VALIDATION R297](VALIDATION.md) (가)~(다)).
- 참가자 보내기는 인원과 상관없이 약 2.3 KB/s다(40바이트 × 초당 60번). 프레임이 60보다 낮으면 그만큼 줄어든다. (R306) 입력이 바뀐 프레임에도 바로 보내 많아야 초당 120번, 4.7 KB/s다.
- **(R306) 어느 열이 실제 값인가:** 방장이 스냅샷마다 "받는 사람 수 × (30 + 65 × 말 수) × 60 ≤ 128 KB/초"를 보고 고른다(Core `SnapshotRate`, 봇은 받지 않지만 말 수에는 든다). 사람만이면 **6명까지 60번 열**, 7명부터 30번 열이다(6명 123.0 KB/s, 7명 60번이면 170.5 KB/s라 30번). 봇으로 12명을 채우면 사람 2~3명(받는 사람 1~2)까지 60번이다(받는 사람 2 × 810 × 60 = 95 KB/s, 3이면 142 KB/s라 30번). 작업 지시서의 예("4명 이하")보다 넓게 잡은 것은 12명 30번(261 KB/s)의 절반 아래라서다. 폰 러쉬 코스 상태는 60번일 때도 초당 30번으로 둔다. 소드 파이트는 스냅샷마다 칼 상태가 붙어(6명 약 115바이트) 6명 60번이면 방장 보내기 약 157 KB/s다(12명 30번 설계 최대보다 작음).

1. A: `F3` → **테스트 방 만들기** → **방 번호 복사** → B·C에게 보낸다(카톡 등).
2. B·C: `F3` → "방 번호" 칸에 붙여넣기 → **참가**.
3. A: **시작 (3명)**.
4. 셋 다 `F3`로 창을 닫고 화면을 클릭한다(마우스 조작이 켜짐).
5. **오른쪽 위 첫 줄로 내 역할을 확인한다:** "네트워크 · 방장" / "네트워크 · 참가자". A가 아닌 PC가 방장이 될 수 있다(§1.3). 누가 방장이 됐는지 적는다.

조작: 폰 러쉬 기물은 왼쪽 창, 퀸 오브 더 힐은 Z/X. 스킬 F, 조준 스킬은 F 뒤 좌클릭(우클릭은 취소). F12 지연 시뮬레이터, Esc 마우스 풀기.

## 8.7 R118 (10-11): 2인 시험 뒤에 바꾼 것

승규 님: "방장 성능 수치 보이기 해줘. 근데 특정 기물이 스킬을 쓸 때 노란색·빨간색까지 보이고, 특히 나이트는 눈에 보일 만큼 지연이 심했고 버그가 있었어. 나도 움직이고 상대도 움직일 때 내가 상대를 밟을 때 멀리 날아간다거나."

| 무엇 | 바뀐 것 |
|---|---|
| **P1 방장 성능 수치** | 오른쪽 위 상자 아래에 **"방장 PC" / "내 PC": 프레임 ms(fps) · 물리 ○/120번/초**, 그리고 Steam 경기면 **방장 고르기** 줄: 사람마다 성능 점수(프레임 반영) · PC만 점수 · 평균 핑 · 방장(★) 또는 다음 방장 몇 번째. 방장이 바뀔 때 메시지("성능이 더 좋은 ○○ 님의 PC가 방장을 맡습니다" 등)를 상자 맨 위에 6초 노랗게 띄운다(전에는 스킬 시험 화면에 안 떴음) |
| **누름 → 반응 재기** | 스킬을 시작할 수 있는 누름만 잰다: 쿨타임이 끝났고 서 있고 땅에 있을 때(폰 러쉬 나이트·룩은 공중도), 나이트 도약 중 두 번째 F, 교대 수락, 조준 클릭. 전에는 쿨타임·공중에서 누른 F도 시계를 켜서 나중에 나간 스킬까지의 시간이 섞였다(왕복 25 ms인데 평균 400~700 ms). **나이트 두 번째 F**는 착지까지가 아니라 방장이 "다시 차고 나감/머리로 날아감"을 한 때까지 |
| **퀸 오브 더 힐 미리 그림** | 땅에 있을 때만 예고를 먼저 그린다(방장도 땅에서만 시작). 2인 시험의 되돌림 10/57은 대부분 폰이 공중에서 누른 것 |
| **나이트 머리 찍기가 상대를 멀리 날림** | 원인: 공중 F로 머리를 향해 날아갈 때 "남은 시간으로 나눈 속도"로 매 물리 단계 다시 겨냥했다. 상대가 마지막 순간에 움직이면 남은 시간이 0에 가까워 나이트가 초속 20 m 넘게 날아가 머리와 부딪혔다(혼자 시험의 더미는 가만히 있어서 안 보였음). 고침: 마지막 0.1초는 다시 겨냥하지 않고, 수평 속도는 `knightHomingSpeed`의 1.25배(약 8.8 m/s), 위아래는 −12~8 m/s까지 |

**나이트가 눈에 보이게 늦은 것**은 위 측정 문제와 별개로 실제로 있다. 나이트는 빠르게 크게 움직여서 몸이 "왕복 + 약 100 ms" 늦게 보이는 것이 다른 기물보다 눈에 띈다. 공중 F(두 번째 누름)는 미리 그리지 않아 이 지연이 그대로 보인다. 줄이는 길은 §7 **P2**(스냅샷 60번, 약 40 ms)와 **P3**(내 말 덜 늦게 그리기, 약 35~70 ms)다. 고친 측정으로 다시 재면 나이트 공중 F의 실제 반응 시간이 나온다.

## 9. 시험 뒤에

- Claude가 할 일: 보내 준 캡처·수치를 [VALIDATION](VALIDATION.md) R117 표에 적고, §6·§8.4 예상값과 비교한다. 크게 다르면 원인부터 찾는다.
- 그다음 §7 "권하는 순서"에서 조건이 맞은 것부터 한다. 기본은 **P1(방장 성능 수치) → 시험 5 결과로 P7 → 느낌에 따라 P2·P3 또는 P4**.
- 결과에 따라 이 문서의 "예상"을 "잰 값"으로 바꿔 적는다.

## 12. R521 (11-09): F3 측정 상자를 간단한 카드로

승규 님: "F3 키를 누르면 … 글자가 너무 작고 잘 안 보여. 심플하게 멀티 플레이에서 중요한 정보만 모던하게 표시해 주고, 적정값이면 초록색, 아슬아슬하면 주황색, 위험하면 빨간색으로." **사람이 보지 않았다**(자동 테스트 · 컴파일 · AI 캡처만) → [VALIDATION R521](VALIDATION.md). 패킷 · 프로토콜은 그대로(v27).

- **F3 한 번 = 카드, 두 번 = 예전 자세한 줄**(§10 · §11 측정 순서가 읽는 줄 그대로), **세 번 = 닫기**. 둘 다 화면 높이에 맞춰 커진다(1080p = 1배, 1440p = 1.33배, 4K = 2배).
- 카드 맨 위: 방장(금색) 또는 참가자(파랑) · 인원 · 가장 나쁜 줄의 판정(좋음 · 주의 · 위험, 잴 것이 아직 없으면 "재는 중"). 줄마다 색 점과 색 숫자, 회색은 아직 잴 것이 없음.
- 방장 줄: 화면 프레임 · 물리 속도(그 1초에 실제로 돈 물리 단계 ÷ 실제 시간이 요구한 단계) · 경기 모습 보내기(초당 번, 목표와 함께) · 업로드 · 참가자 최고 핑(Steam 핑, 직접 · 릴레이 수). 사람 참가자가 없으면(봇만) 아래 셋 대신 회색 "참가자 · 아직 없음 (봇만)".
- 참가자 줄: 핑(게임이 잰 왕복, 직접/릴레이 연결) · 조작 반응(누른 뒤 내 몸이 움직여 보이기까지) · 손실 · 흔들림 · 경기 모습 받기(초당 번) · 화면 프레임.
- 아래 줄: 자동 입력 · `-latencyBefore`이면 그 표시, 오른쪽에 "F3 자세히".
- 재는 법: 1초마다 새로 잰다. 화면 프레임은 그 1초의 평균(자세한 줄의 `프레임 ms`는 예전처럼 부드럽게 한 값). 상자가 붙은 첫 프레임(대개 장면 로딩)과 그 전의 물리 단계는 빼고, 그다음 1초도 재기만 하고 보여 주지 않는다(카드에는 회색 "—"). Unity가 처음 몇 프레임을 실제 시간과 상관없이 0.02초로 돌려서(임시 빌드: 1.15초 지난 프레임에 0.02초) 그 1초는 늘 `1 fps · 1%` 빨강이었다.
- 처음 F3의 멈춤: Unity 6 IMGUI는 글자를 처음 재거나 그릴 때 그 글자를 만든다(임시 빌드에서 한 글자 1.5~3 ms, 그 뒤로는 어떤 크기 · 굵기든 공짜). 그래서 카드의 첫 F3이 0.9초 멈췄다(방장이면 모두의 경기가 멈춤). 이제 상자의 첫 프레임(경기 장면 시작)에 카드와 자세한 줄이 쓸 글자를 한 번씩 재 둔다(`Warm`, 상자 자신의 문장 만들기를 샘플 숫자로 돌림). 임시 빌드: 경기 시작에 0.64초 더(처음 띄운 게임 기준), 첫 F3 그리기 0.9초 → 11 ms([PITFALLS 71](../Environment/PITFALLS.md)).
- 글자 색: 이 프로젝트는 선형 색 공간이라 IMGUI 글자만 색이 한 번 더 어둡게 나온다(주황 `#FFA23A` → `#FF5C0A`, 회색 설명은 거의 검정, 같은 색의 점 · 판은 정확). 그래서 글자 색만 `Color.gamma`로 바꿔 넘긴다([PITFALLS 70](../Environment/PITFALLS.md)).
- 기준은 Core `NetHealth` 한 곳(테스트가 아래 근거의 게임 숫자와 맞는지 확인), 경로 숫자는 Core `RouteSummary`(`SteamRoute.Summary`가 1초에 한 번 채움, 같은 값으로 자세한 줄의 `연결`도 씀).
