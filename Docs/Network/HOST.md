# 방장(호스트) 선정·이전 (`HostElection`, `HostFitnessProbe`, `SteamSession`)

코드: `Scripts/Core/HostElection.cs`(점수·순위·후계자, 순수 C#), `Scripts/Network/HostFitnessProbe.cs`(PC 측정), `Scripts/Network/SteamSession.cs`(선정·이전), `Scripts/Network/SteamMotion.cs`(캡슐), `ChessFight/RagdollLabSteam/SteamRagdollLink.cs`(래그돌 랩).

상태: **코드·모의 테스트·실제 Unity/Steamworks DLL 컴파일만 통과. Unity·Steam에서 사람이 본 것은 없다.** 브랜치 `claude/host-migration`(R50, 승규 님 요청). 확인 목록은 [VALIDATION](VALIDATION.md) 최상단.

## 1. 왜 필요한가

이 게임은 전용 서버가 없다. **방장 PC 한 대가 모든 캐릭터를 계산**한다. 래그돌 랩에서는 모든 래그돌의 물리를 1초에 120번(관절 솔버 24회) 계산한다. 그래서:

- 방장 PC가 느리면 **모든 참가자가 렉**을 겪는다(2026-09-27 팀 테스트에서 실제로 관찰).
- 예전에는 방을 만든 사람이 끝까지 방장이었고, **방장이 나가면 경기가 통째로 끝났다.**

## 2. 한눈에

| 상황 | 예전 | 지금 |
|---|---|---|
| 경기 시작 | 방을 만든 사람이 방장 | **가장 적합한 PC**가 방장. 만든 사람보다 15% 이상 좋을 때만 넘긴다 |
| 방장이 게임을 끄거나 "나가기" | 경기 종료, 모두 파티로 | **다음 방장이 이어받고 경기 계속** |
| 방장 게임이 죽음(크래시) | 최대 12초 멈춘 뒤 종료 | Steam이 방장을 방에서 빼는 즉시 다음 방장 |
| 방장이 방에는 있는데 응답 없음(인터넷 끊김 등) | 12초 뒤 종료 | **4초** 뒤 다음 방장(시작·교체 직후 10초는 제외: 씬 로딩 멈춤과 구별) |
| 방장 PC가 계속 느림 | 그대로 | 평균 25fps 미만이 **5초** 넘게 이어지고, 하드웨어 점수가 **1.5배 이상**인 사람이 있으면 넘김(시작·교체 후 45초 동안은 안 함) |
| 시작 전 대기실에서 방장이 나감 | 방 닫힘 | 그대로(파티 예약은 옮길 수 없다) |
| 방장 말고 다른 사람이 나감 | 명단에서 빠짐 | 그대로 |

## 3. 적합도 점수

모든 값은 **시험값**이다. 비율만 의미가 있고, 보통 데스크톱이 1000 근처가 되게 맞췄다.

| 단계 | 계산 | 코드 |
|---|---|---|
| 벤치마크 | 게임을 켜고 1.5초 뒤, 뒤쪽 스레드에서 물리 비슷한 계산(물체 256개 × 6000스텝)을 3번 해서 가장 빠른 시간. 이 PC(16스레드) Unity Mono 기준 약 30ms | `HostFitnessProbe` |
| 기계 점수(Base) | 1000 × 40ms ÷ 벤치마크 ms × (0.75 + 0.25 × min(코어, 8) ÷ 8) × (메모리 8GB 미만이면 0.85) × (Unity 에디터면 0.85) | `HostFitness.Base` |
| 현재 점수(fit) | 기계 점수 × (평균 프레임이 25ms보다 길면 25 ÷ 프레임 ms) | `HostFitness.WithFrames` |
| 핑 반영 | 다른 사람들과의 **평균** 예상 핑(Steam 핑 위치)이 60ms를 넘으면 × 60 ÷ 핑(최소 0.3배). 최악이 아니라 평균인 이유: 먼 곳의 한 명은 누가 방장이든 멀다 | `HostElection.Rating` |

- **벤치마크를 쓰는 이유:** 수직 동기화가 켜져 있으면 빠른 PC도 보통 PC도 로비에서 60fps로 똑같이 보인다.
- **느린 방장을 넘길 때는 기계 점수끼리 비교한다.** 현재 점수로 비교하면, 넘겨받은 PC가 방장 일로 느려지는 순간 원래 PC가 다시 빨라 보여서 방장이 왔다 갔다 한다(`HostElection.Takeover`).
- 점수가 없는 사람(측정 전)은 300으로 친다. 측정된 사람보다 앞서지 않는다.
- 같은 점수면 Steam ID가 작은 사람. 모든 PC가 같은 순서를 얻는다.

## 4. 로비에 올리는 값

**경기 로비 데이터**(방 주인만 쓸 수 있다)

| 키 | 값 |
|---|---|
| `host` | 방장 Steam ID |
| `epoch` | 방장 번호. 방장이 바뀔 때마다 1씩 오른다. 시작 = 1 |
| `successors` | 다음 방장 순서 `id,id,…`. 방장이 2초마다 갱신. 크래시처럼 의논할 틈이 없을 때 모두가 이 순서를 따른다 |
| `seats`, `held`, `open`, `free0`/`free1` | (R52) 빈자리 채우기: 시작 때 팀별 인원, 오는 중인 파티원의 잡아 둔 자리(기한은 Steam 서버 시각). 새 방장은 방 주인이 되면 이것을 읽어 이어간다 → [SESSION §8](SESSION.md#8-빈자리-채우기-r52-2026-09-30) |

**멤버 데이터**(각자 자기 것)

| 키 | 값 |
|---|---|
| `fit` | 현재 점수. 15% 넘게 바뀔 때만, 2초에 한 번까지 다시 올림 |
| `base` | 기계 점수 |
| `loc` | Steam 핑 위치(문자열). Steam이 측정한 뒤 한 번 |
| `claim` | "내가 이 번호의 방장이다". 방 주인이 되기 전의 새 방장이 쓴다 |

## 5. 흐름

```text
[시작]  방장이 점수·핑으로 순위를 매김 → 1등이 15% 이상 좋으면 그 사람으로
        host·epoch=1·successors를 먼저 쓰고 → phase=playing → 방 주인도 넘김(SetLobbyOwner)
[경기 중] 방장이 2초마다 successors 갱신
[방장 사라짐] 방에서 빠짐(즉시) 또는 4초 넘게 응답 없음
        → successors에서 방에 남은 첫 사람 = 새 방장
        → 새 방장: epoch+1로 claim → (방 주인이 아니면) 지금 방 주인이 SetLobbyOwner로 넘겨줌
        → 새 방장이 방 주인이 되면 host·epoch를 씀
        → 나머지: 더 높은 epoch를 보면 따라감
[옛 방장이 돌아옴] 더 높은 epoch의 claim을 보고 참가자로 물러남(방 주인이면 넘겨줌)
```

**번호 규칙:** 볼 수 있는 기록 중 가장 높은 `epoch`가 이긴다(로비 기록 또는 방에 있는 사람의 `claim`). 같은 번호면 로비 기록, 그다음 작은 Steam ID. 그래서 두 사람이 동시에 나서도 한 명으로 정리된다.

**Steam 로비 주인 ≠ 게임 방장.** Steam은 주인이 나가면 아무에게나 주인을 넘긴다. 이제는 그 사람이 방장이 되는 게 아니라, 정해진 새 방장에게 주인을 넘겨준다(주인만 로비 데이터를 쓸 수 있어서).

## 6. 방장이 바뀔 때 화면 쪽

| | 새 방장 | 나머지(옛 방장 포함) |
|---|---|---|
| 캡슐 (`SteamMotion`) | 마지막 스냅샷 위치에서 이어서 계산. tick은 이어서 센다. 점프 누른 횟수는 첫 입력을 기준값으로 삼는다(바뀌자마자 모두 뛰는 것 방지) | 예측 중이던 입력을 비우고 새 방장에게 보낸다 |
| 래그돌 랩 (`SteamRagdollLink`) | 가장 최근에 받은 자세를 적용한 뒤 물리를 켠다(`SetNetworkPuppet(false)`), 퀸 오브 더 힐 판정 권한, 과부하 보호 켬 | 모든 래그돌을 인형(puppet)으로. 받은 자세만 그린다 |
| 화면 | 상태 줄 6초: "이 PC가 방장을 맡았습니다" | "방장이 ○○ 님으로 바뀌었습니다". 경기 명단에 `· 방장` |

아무도 다시 스폰되지 않는다. 대신 **약 0.1초 전 자세에서 속도 0으로 이어서** 잠깐 멈칫한다.

## 7. 렉 줄이기 — 함께 고친 것

| 고친 것 | 이유 |
|---|---|
| 스냅샷을 **정해진 일정**으로 보냄(캡슐 20Hz, 래그돌 30Hz, 래그돌 입력 60Hz) | 예전 방식("마지막 전송 뒤 50ms 지났나")은 매번 다음 프레임으로 밀려, 60fps 방장이 실제로는 초당 약 17번, 들쭉날쭉 보냈다 |
| 받은 메시지를 **프레임마다 끝까지** 읽음 | 12명이면 초당 330개 입력. 한 프레임 32개(래그돌 64개)만 읽으면 방장 fps가 떨어질 때 읽지 못한 입력이 쌓여 지연이 계속 커졌다 |
| 래그돌 방장 **과부하 보호**: 방장인 동안 `Time.maximumDeltaTime` 0.1초 | 기본값(1/3초)이면 느린 방장이 한 프레임에 물리 40번을 몰아 계산하느라 멈췄다가 한꺼번에 보낸다(참가자에게 끊김·순간이동). 0.1초면 최대 12번이라, 느린 방장은 조금 느리게 돌지만 스냅샷이 고르게 나간다. 경기가 끝나거나 방장을 넘기면 원래 값으로 돌린다 |

## 8. 한계

- **시작 전(대기실)에는 이전하지 않는다.** 파티 예약이 방장 PC에만 있어서다.
- 방장이 방에는 남아 있고 **한 사람과의 연결만** 끊긴 경우는 이전하지 않는다(다른 사람은 잘 받고 있으므로). 그 사람만 12초 뒤 파티로 돌아간다.
- 새 방장은 **받은 자세에서** 이어가므로 속도(날아가던 중이던 것)는 이어지지 않는다.
- 벤치마크는 CPU만 잰다. 그래픽 성능은 프레임 시간으로만 반영된다.
- 프로토콜 **v8**. v7 빌드와는 매칭되지 않는다.
- 봇은 절대 방장이 되지 않는다(Steam 계정이 없다). 새 방장이 봇 계산을 이어받는다.
- (R52) 빈자리에 들어와 **아직 자리를 기다리는 사람**은 방장 교체에 끼지 않는다(후계자 계산도, 후보도 아님). 자리를 받은 뒤부터 후보가 된다. 나간 방장의 자리도 빈자리가 되어 매칭으로 채운다.
- (R52) 방장이 파티장이어도 **방장만** 나간다. 그 파티원들은 경기에 남고, 방장 역할은 남은 사람 중 가장 적합한 PC로 넘어간다([SESSION §6](SESSION.md#6-취소퇴장호스트-이탈)).

## 9. 자동 테스트

| 종류 | 테스트 |
|---|---|
| Core (`NetworkCoreTests`) | 점수(벤치마크·코어·메모리·에디터·프레임), 순위(핑 할인, 같은 점수, 봇 제외, 15% 여유), 느린 방장(기계 점수 1.5배, 되돌아가지 않음), 후계자(없는 사람 건너뜀, 나가는 사람 제외), 프레임 감시(5초 지속, 로딩 한 번은 무시) |
| 세션 (`SessionFlowTests`, 모의 Steam) | 시작 때 좋은 PC로 넘김 / 6% 차이는 안 넘김 / 먼 PC는 안 됨 / 크래시 → 후계자 / Steam이 다른 사람에게 주인을 줘도 후계자에게 감 / 방장이 나가도 경기 계속 / 응답 없는 방장 교체와 복귀한 옛 방장 물러남 / 계속 느린 방장 / (R52) 파티의 잡아 둔 빈자리가 방장 크래시 뒤에도 이어짐 |

모의 Steam은 로비·주인·멤버 데이터만 흉내 낸다. **실제 전송, 실제 Steam의 주인 이전 속도, 크래시 뒤 방에서 빠지기까지의 시간은 확인하지 못했다.**
