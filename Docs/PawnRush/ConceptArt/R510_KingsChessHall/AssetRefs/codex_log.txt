# Image Generation Skill

Generates or edits images for the current project (for example website assets, game assets, UI mockups, product mockups, wireframes, logo design, photorealistic images, or infographics).

## Top-level modes and rules

This skill has exactly two top-level modes:

- **Default built-in tool mode (preferred):** built-in `image_gen` tool for image generation, editing, and transparent-image requests. Does not require `OPENAI_API_KEY`.
- **Fallback CLI mode:** `scripts/image_gen.py` CLI. Use when the user explicitly asks for or confirms the CLI/API/model path. Requires `OPENAI_API_KEY`.

Within CLI fallback, the CLI exposes three subcommands:

- `generate`
- `edit`
- `generate-batch`

Rules:
- Use the built-in `image_gen` tool by default for normal image generation and editing requests.
- Do not switch to CLI fallback for ordinary quality, size, or file-path control.
- For transparent images, ask built-in `image_gen` for a transparent background and preserve the generated alpha.
- Never silently switch from built-in `image_gen` or CLI `gpt-image-2` to CLI `gpt-image-1.5`; ask the user first unless they explicitly requested `gpt-image-1.5`.
- The word `batch` by itself does not mean CLI fallback. If the user asks for many assets or says to batch-generate assets without explicitly asking for CLI/API/model controls, stay on the built-in path and issue one built-in call per requested asset or variant.
- If the built-in tool fails or is unavailable, tell the user the CLI fallback exists and that it requires `OPENAI_API_KEY`. Proceed only if the user explicitly asks for that fallback.
- If the user explicitly asks for CLI mode, use the bundled `scripts/image_gen.py` workflow. Do not create one-off SDK runners.
- Never modify `scripts/image_gen.py`. If something is missing, ask the user before doing anything else.

Built-in save-path policy:
- In built-in tool mode, Codex saves generated images under `$CODEX_HOME/*` by default.
- Do not describe or rely on OS temp as the default built-in destination.
- Do not describe or rely on a destination-path argument (if any) on the built-in `image_gen` tool. If a specific location is needed, generate first and then move or copy the selected output from `$CODEX_HOME/generated_images/...`.
- Save-path precedence in built-in mode:
  1. If the user names a destination, move or copy the selected output there.
  2. If the image is meant for the current project, move or copy the final selected image into the workspace before finishing.
  3. If the image is only for preview or brainstorming, render it inline; the underlying file can remain at the default `$CODEX_HOME/*` path.
- Never leave a project-referenced asset only at the default `$CODEX_HOME/*` path.
- Do not overwrite an existing asset unless the user explicitly asked for replacement; otherwise create a sibling versioned filename such as `hero-v2.png` or `item-icon-edited.png`.

Shared prompt guidance for both modes lives in `references/prompting.md` and `references/sample-prompts.md`.

Fallback-only docs/resources for CLI mode:
- `references/cli.md`
- `references/image-api.md`
- `references/codex-network.md`
- `scripts/image_gen.py`

## When to use
- Generate a new image (concept art, product shot, cover, website hero)
- Generate a new image using one or more reference images for style, composition, or mood
- Edit an existing image (inpainting, lighting or weather transformations, background replacement, object removal, compositing, transparent background)
- Produce many assets or variants for one task

## When not to use
- Extending or matching an existing SVG/vector icon set, logo system, or illustration library inside the repo
- Creating simple shapes, diagrams, wireframes, or icons that are better produced directly in SVG, HTML/CSS, or canvas
- Making a small project-local asset edit when the source file already exists in an editable native format
- Any task where the user clearly wants deterministic code-native output instead of a generated bitmap

## Decision tree

Think about two separate questions:

1. **Intent:** is this a new image or an edit of an existing image?
2. **Execution strategy:** is this one asset or many assets/variants?

Intent:
- If the user wants to modify an existing image while preserving parts of it, treat the request as **edit**.
- If the user provides images only as references for style, composition, mood, or subject guidance, treat the request as **generate**.
- If the user provides no images, treat the request as **generate**.

Built-in edit semantics:
- Built-in edit mode is for images already visible in the conversation context, such as attached images or images generated earlier in the thread.
- If the user wants to edit a local image file with the built-in tool, first load it with built-in `view_image` tool so the image is visible in the conversation context, then proceed with the built-in edit flow.
- Do not promise arbitrary filesystem-path editing through the built-in tool.
- If a local file still needs direct file-path control, masks, or other explicit CLI-only parameters, use the explicit CLI fallback only when the user asks for it.
- For edits, preserve invariants aggressively and save non-destructively by default.

Execution strategy:
- In the built-in default path, produce many assets or variants by issuing one `image_gen` call per requested asset or variant.
- In the CLI fallback path, use the CLI `generate-batch` subcommand only when the user explicitly chose CLI mode and needs many prompts/assets.
- For many distinct assets, do not use `n` as a substitute for separate prompts. `n` is for variants of one prompt; distinct assets need distinct built-in calls or distinct CLI `generate-batch` jobs.

Assume the user wants a new image unless they clearly ask to change an existing one.

## Workflow
1. Decide the top-level mode: built-in by default, including transparent-output requests; fallback CLI only if explicitly requested or confirmed.
2. Decide the intent: `generate` or `edit`.
3. Decide whether the output is preview-only or meant to be consumed by the current project.
4. Decide the execution strategy: single asset vs repeated built-in calls vs CLI `generate-batch`.
5. Collect inputs up front: prompt(s), exact text (verbatim), constraints/avoid list, and any input images.
6. For every input image, label its role explicitly:
   - reference image
   - edit target
   - supporting insert/style/compositing input
7. If the edit target is only on the local filesystem and you are staying on the built-in path, inspect it with `view_image` first so the image is available in conversation context.
8. If the user asked for a photo, illustration, sprite, product image, banner, or other explicitly raster-style asset, use `image_gen` rather than substituting SVG/HTML/CSS placeholders. If the request is for an icon, logo, or UI graphic that should match existing repo-native SVG/vector/code assets, prefer editing those directly instead.
9. Augment the prompt based on specificity:
   - If the user's prompt is already specific and detailed, normalize it into a clear spec without adding creative requirements.
   - If the user's prompt is generic, add tasteful augmentation only when it materially improves output quality.
10. Use the built-in `image_gen` tool by default.
11. For transparent-output requests, ask built-in `image_gen` for a transparent background and preserve the generated alpha channel.
12. Inspect outputs and validate: subject, style, composition, text accuracy, and invariants/avoid items.
13. Iterate with a single targeted change, then re-check.
14. For preview-only work, render the image inline; the underlying file may remain at the default `$CODEX_HOME/generated_images/...` path.
15. For project-bound work, move or copy the selected artifact into the workspace and update any consuming code or references. Never leave a project-referenced asset only at the default `$CODEX_HOME/generated_images/...` path.
16. For batches or multi-asset requests, persist every requested deliverable final in the workspace unless the user explicitly asked to keep outputs preview-only. Discarded variants do not need to be kept unless requested.
17. If the user explicitly chooses or confirms the CLI fallback, then use the fallback-only docs for model, quality, size, `input_fidelity`, masks, output format, output paths, and network setup.
18. Always report the final saved path(s) for any workspace-bound asset(s), plus the final prompt or prompt set and whether the built-in tool or fallback CLI mode was used.

## Prompt augmentation

Reformat user prompts into a structured, production-oriented spec. Make the user's goal clearer and more actionable, but do not blindly add detail.

Treat this as prompt-shaping guidance, not a closed schema. Use only the lines that help, and add a short extra labeled line when it materially improves clarity.

### Specificity policy

Use the user's prompt specificity to decide how much augmentation is appropriate:

- If the prompt is already specific and detailed, preserve that specificity and only normalize/structure it.
- If the prompt is generic, you may add tasteful augmentation when it will materially improve the result.

Allowed augmentations:
- composition or framing hints
- polish level or intended-use hints
- practical layout guidance
- reasonable scene concreteness that supports the stated request

Not allowed augmentations:
- extra characters or objects that are not implied by the request
- brand names, slogans, palettes, or narrative beats that are not implied
- arbitrary side-specific placement unless the surrounding layout supports it

## Shared prompt schema

Use the following labeled spec as shared prompt scaffolding for both top-level modes:

```text
Use case: <taxonomy slug>
Asset type: <where the asset will be used>
Primary request: <user's main prompt>
Input images: <Image 1: role; Image 2: role> (optional)
Scene/backdrop: <environment>
Subject: <main subject>
Style/medium: <photo/illustration/3D/etc>
Composition/framing: <wide/close/top-down; placement>
Lighting/mood: <lighting + mood>
Color palette: <palette notes>
Materials/textures: <surface details>
Text (verbatim): "<exact text>"
Constraints: <must keep/must avoid>
Avoid: <negative constraints>
```

Notes:
- `Asset type` and `Input images` are prompt scaffolding, not dedicated CLI flags.
- `Scene/backdrop` refers to the visual setting. It is not the same as the fallback CLI `background` parameter, which controls output transparency behavior.
- Fallback-only execution notes such as `Quality:`, `Input fidelity:`, masks, output format, and output paths belong in the CLI path only. Do not treat them as built-in `image_gen` tool arguments.

Augmentation rules:
- Keep it short.
- Add only the details needed to improve the prompt materially.
- For edits, explicitly list invariants (`change only X; keep Y unchanged`).
- If any critical detail is missing and blocks success, ask a question; otherwise proceed.

## Prompting best practices
- Structure prompt as scene/backdrop -> subject -> details -> constraints.
- Include intended use (ad, UI mock, infographic) to set the mode and polish level.
- Use camera/composition language for photorealism.
- Only use SVG/vector stand-ins when the user explicitly asked for vector output or a non-image placeholder.
- Quote exact text and specify typography + placement.
- For tricky words, spell them letter-by-letter and require verbatim rendering.
- For multi-image inputs, reference images by index and describe how they should be used.
- For edits, repeat invariants every iteration to reduce drift.
- Iterate with single-change follow-ups.
- If the prompt is generic, add only the extra detail that will materially help.
- If the prompt is already detailed, normalize it instead of expanding it.
- For CLI fallback only, see `references/cli.md` and `references/image-api.md` for model, `quality`, `input_fidelity`, masks, output format, and output-path guidance.
- For transparent images, ask built-in `image_gen` for actual transparency and preserve its alpha.

## gpt-image-2 guidance for CLI fallback

The fallback CLI defaults to `gpt-image-2`.

- Use `gpt-image-2` for new CLI/API workflows unless the user confirms a different model.
- CLI `gpt-image-2` does not support `background=transparent`; ask before using `gpt-image-1.5` unless the user explicitly requested that model.
- `gpt-image-2` always uses high fidelity for image inputs; do not set `input_fidelity` with this model.
- `gpt-image-2` supports `quality` values `low`, `medium`, `high`, and `auto`.
- Use `quality low` for fast drafts, thumbnails, and quick iterations. Use `medium`, `high`, or `auto` for final assets, dense text, diagrams, identity-sensitive edits, or high-resolution outputs.
- Square images are typically fastest to generate. Use `1024x1024` for fast square drafts.
- If the user asks for 4K-style output, use `3840x2160` for landscape or `2160x3840` for portrait.
- `gpt-image-2` size may be `auto` or `WIDTHxHEIGHT` if all constraints hold: max edge `<= 3840px`, both edges multiples of `16px`, long-to-short ratio `<= 3:1`, total pixels between `655,360` and `8,294,400`.

Popular `gpt-image-2` sizes:
- `1024x1024` square
- `1536x1024` landscape
- `1024x1536` portrait
- `2048x2048` 2K square
- `2048x1152` 2K landscape
- `3840x2160` 4K landscape
- `2160x3840` 4K portrait
- `auto`

## 2. 무엇이 되고 무엇이 안 되는가

- **현재 편집할 폰 러시**: `ChessFight → Pawn Rush → Open Section Test`.
- **미니게임만 선택**: `ChessFight → Pawn Rush → Open Mini-game Prefab Test`; 숫자1~0, F5 팀, F8 초기화.
- C/D/A는 초반, B/E/F/J는 중반, G/H/I는 후반 후보로 슬롯2/4/6에3/4/3개 등록돼 있다.
- 슬롯1 정원 → 슬롯2 초반 미니게임 → 슬롯3 홀 → 슬롯4 중반 미니게임 → 슬롯6 후반 미니게임 → 슬롯7 작전 회의실로 이어진다.
- 미니게임의 건축·장식은 저장된 프리팹이다. Play에는 Game socket의 기능 게임만 다시 설치한다.
- 자동 완료(F6/ForceComplete)는 이벤트·팀 문 연결 검사다. 실제 장치를 풀어서 달성했다는 뜻이 아니다.
- 정원·홀·작전 회의실의 일부 아트는 Play에 만들어진다. 편집 모드의 빈 루트만 보고 자산 누락으로 판단하지 않는다.
- **Prototype Course01**은 기존 온라인 경기가 호출하는 씬이다. 씬 이름 `PawnRush_Course01`, 로비 키 `kingrush`, 기존 통신 구조는 유지한다.
- `GameModes.KingRush` 이름과 `ModeRetiredQueenHill = 1` 같은 예약 통신 값은 파일 정리 때문에 바꾸지 않는다.
- Queen of the Hill을 새 모드로 다시 등록하지 않는다. Queen 기물 자체는 다른 모드가 쓰므로 유지한다.
- 새 Sections 코스를 기존 Course01 온라인 흐름에 연결했다고 말하지 않는다. 기존 Steam 흐름의 변경도 이번 범위가 아니다.
- R497 실제 Unity 저장10프리팹/시험 씬 실패0, Play10종의 기능 캐시·자기 팀 문·2번 초기화·씨앗 재생성·A 인스턴스 분리·I 외형 유지 자동 검사 통과. [VALIDATION](Docs/Network/VALIDATION.md)에 범위와 한계를 기록했다.
- AI의 컴파일·자동 검사·렌더 관찰과 사용자가 Unity/Steam에서 직접 보고 조작한 확인을 구분한다.

## 4. 절대 규칙 — 어기면 과거에 실제로 사고가 났던 것들

1. **Active Input Handling은 `Input Manager (Old)`(0)로 둔다. Input System 패키지는 설치하지 않는다**(`JY-lobby`, R20: 설치돼 있으면 켤 때마다 백엔드를 켜라는 창이 뜬다). uGUI가 없어서 Both/New로 바꾸면 HUD 클릭과 입력이 전부 죽는다. `InputSettingsGuard`가 자동으로 되돌린다. → [PITFALLS §1](Docs/Environment/PITFALLS.md)
2. **프로젝트는 선택 패키지가 하나도 없어도 컴파일되어야 한다.** Safe Mode에서는 설치 스크립트가 돌지 않는다. 선택 패키지 코드는 전용 asmdef + `versionDefines` + `defineConstraints`로 가둔다. `ENABLE_INPUT_SYSTEM`을 패키지 설치 여부로 쓰지 않는다.
3. **`Packages/manifest.json`·`packages-lock.json`이 바뀌면 Discard하지 말고 커밋한다.**
4. **폴더 하나 = 어셈블리 하나.** `Game`·`Gameplay`는 Steam을 참조하지 않는다. `Core`는 Unity도 참조하지 않는다. → [Architecture/STRUCTURE](Docs/Architecture/STRUCTURE.md)
5. **Steam 초기화·종료 소유자는 `NetworkRuntime` 하나다.** SteamManager를 따로 추가하지 않는다.
6. **HUD에는 기본 테마가 없다.** ScrollView·Dropdown 같은 복합 컨트롤은 보이지 않는다. 평범한 VisualElement만 쓴다.
7. **장애물 위치·회전은 `ObstacleClock` 시간의 순수 함수로만 계산한다(스스로 움직이는 kinematic 물체는 `Obstacle`을 상속, 테스트 스크립트가 검사. 플레이어 상태로 움직이는 것은 `StateDrivenMover:` 주석을 달고 오프라인 전용).** 프레임마다 누적하지 않는다. 온라인 래그돌 참가자는 방장이 스냅샷에 실은 장애물 시각을 쓴다(R51).
8. **클라이언트는 입력만 보낸다.** 좌표를 권위로 받지 않는다. 파티는 같은 팀에 통째로 예약한다.
9. **네트워크 비호환 변경을 하면 `SteamSession.Protocol`을 올린다.** 패킷 구조를 바꾸면 `MotionProtocol` magic도 올린다.
10. **검증 표기는 정직하게 한다.** 사용자가 Unity나 Steam에서 직접 본 것만 VALIDATION에 '성공'으로 적는다. 코드 작성과 테스트 통과는 검증이 아니다.
11. **`.meta`는 항상 같이 커밋한다.** Unity 밖에서 파일을 만들면 `Tools/Generators/mkmeta.py`로 만든다.

# Image Generation Skill

Generates or edits images for the current project (for example website assets, game assets, UI mockups, product mockups, wireframes, logo design, photorealistic images, or infographics).

## Top-level modes and rules

This skill has exactly two top-level modes:

- **Default built-in tool mode (preferred):** built-in `image_gen` tool for image generation, editing, and transparent-image requests. Does not require `OPENAI_API_KEY`.
- **Fallback CLI mode:** `scripts/image_gen.py` CLI. Use when the user explicitly asks for or confirms the CLI/API/model path. Requires `OPENAI_API_KEY`.

Within CLI fallback, the CLI exposes three subcommands:

- `generate`
- `edit`
- `generate-batch`

Rules:
- Use the built-in `image_gen` tool by default for normal image generation and editing requests.
- Do not switch to CLI fallback for ordinary quality, size, or file-path control.
- For transparent images, ask built-in `image_gen` for a transparent background and preserve the generated alpha.
- Never silently switch from built-in `image_gen` or CLI `gpt-image-2` to CLI `gpt-image-1.5`; ask the user first unless they explicitly requested `gpt-image-1.5`.
- The word `batch` by itself does not mean CLI fallback. If the user asks for many assets or says to batch-generate assets without explicitly asking for CLI/API/model controls, stay on the built-in path and issue one built-in call per requested asset or variant.
- If the built-in tool fails or is unavailable, tell the user the CLI fallback exists and that it requires `OPENAI_API_KEY`. Proceed only if the user explicitly asks for that fallback.
- If the user explicitly asks for CLI mode, use the bundled `scripts/image_gen.py` workflow. Do not create one-off SDK runners.
- Never modify `scripts/image_gen.py`. If something is missing, ask the user before doing anything else.

Built-in save-path policy:
- In built-in tool mode, Codex saves generated images under `$CODEX_HOME/*` by default.
- Do not describe or rely on OS temp as the default built-in destination.
- Do not describe or rely on a destination-path argument (if any) on the built-in `image_gen` tool. If a specific location is needed, generate first and then move or copy the selected output from `$CODEX_HOME/generated_images/...`.
- Save-path precedence in built-in mode:
  1. If the user names a destination, move or copy the selected output there.
  2. If the image is meant for the current project, move or copy the final selected image into the workspace before finishing.
  3. If the image is only for preview or brainstorming, render it inline; the underlying file can remain at the default `$CODEX_HOME/*` path.
- Never leave a project-referenced asset only at the default `$CODEX_HOME/*` path.
- Do not overwrite an existing asset unless the user explicitly asked for replacement; otherwise create a sibling versioned filename such as `hero-v2.png` or `item-icon-edited.png`.

Shared prompt guidance for both modes lives in `references/prompting.md` and `references/sample-prompts.md`.

Fallback-only docs/resources for CLI mode:
- `references/cli.md`
- `references/image-api.md`
- `references/codex-network.md`
- `scripts/image_gen.py`

## When to use
- Generate a new image (concept art, product shot, cover, website hero)
- Generate a new image using one or more reference images for style, composition, or mood
- Edit an existing image (inpainting, lighting or weather transformations, background replacement, object removal, compositing, transparent background)
- Produce many assets or variants for one task

## When not to use
- Extending or matching an existing SVG/vector icon set, logo system, or illustration library inside the repo
- Creating simple shapes, diagrams, wireframes, or icons that are better produced directly in SVG, HTML/CSS, or canvas
- Making a small project-local asset edit when the source file already exists in an editable native format
- Any task where the user clearly wants deterministic code-native output instead of a generated bitmap

## Decision tree

Think about two separate questions:

1. **Intent:** is this a new image or an edit of an existing image?
2. **Execution strategy:** is this one asset or many assets/variants?

Intent:
- If the user wants to modify an existing image while preserving parts of it, treat the request as **edit**.
- If the user provides images only as references for style, composition, mood, or subject guidance, treat the request as **generate**.
- If the user provides no images, treat the request as **generate**.

Built-in edit semantics:
- Built-in edit mode is for images already visible in the conversation context, such as attached images or images generated earlier in the thread.
- If the user wants to edit a local image file with the built-in tool, first load it with built-in `view_image` tool so the image is visible in the conversation context, then proceed with the built-in edit flow.
- Do not promise arbitrary filesystem-path editing through the built-in tool.
- If a local file still needs direct file-path control, masks, or other explicit CLI-only parameters, use the explicit CLI fallback only when the user asks for it.
- For edits, preserve invariants aggressively and save non-destructively by default.

Execution strategy:
- In the built-in default path, produce many assets or variants by issuing one `image_gen` call per requested asset or variant.
- In the CLI fallback path, use the CLI `generate-batch` subcommand only when the user explicitly chose CLI mode and needs many prompts/assets.
- For many distinct assets, do not use `n` as a substitute for separate prompts. `n` is for variants of one prompt; distinct assets need distinct built-in calls or distinct CLI `generate-batch` jobs.

Assume the user wants a new image unless they clearly ask to change an existing one.

## Workflow
1. Decide the top-level mode: built-in by default, including transparent-output requests; fallback CLI only if explicitly requested or confirmed.
2. Decide the intent: `generate` or `edit`.
3. Decide whether the output is preview-only or meant to be consumed by the current project.
4. Decide the execution strategy: single asset vs repeated built-in calls vs CLI `generate-batch`.
5. Collect inputs up front: prompt(s), exact text (verbatim), constraints/avoid list, and any input images.
6. For every input image, label its role explicitly:
   - reference image
   - edit target
   - supporting insert/style/compositing input
7. If the edit target is only on the local filesystem and you are staying on the built-in path, inspect it with `view_image` first so the image is available in conversation context.
8. If the user asked for a photo, illustration, sprite, product image, banner, or other explicitly raster-style asset, use `image_gen` rather than substituting SVG/HTML/CSS placeholders. If the request is for an icon, logo, or UI graphic that should match existing repo-native SVG/vector/code assets, prefer editing those directly instead.
9. Augment the prompt based on specificity:
   - If the user's prompt is already specific and detailed, normalize it into a clear spec without adding creative requirements.
   - If the user's prompt is generic, add tasteful augmentation only when it materially improves output quality.
10. Use the built-in `image_gen` tool by default.
11. For transparent-output requests, ask built-in `image_gen` for a transparent background and preserve the generated alpha channel.
12. Inspect outputs and validate: subject, style, composition, text accuracy, and invariants/avoid items.
13. Iterate with a single targeted change, then re-check.
14. For preview-only work, render the image inline; the underlying file may remain at the default `$CODEX_HOME/generated_images/...` path.
15. For project-bound work, move or copy the selected artifact into the workspace and update any consuming code or references. Never leave a project-referenced asset only at the default `$CODEX_HOME/generated_images/...` path.
16. For batches or multi-asset requests, persist every requested deliverable final in the workspace unless the user explicitly asked to keep outputs preview-only. Discarded variants do not need to be kept unless requested.
17. If the user explicitly chooses or confirms the CLI fallback, then use the fallback-only docs for model, quality, size, `input_fidelity`, masks, output format, output paths, and network setup.
18. Always report the final saved path(s) for any workspace-bound asset(s), plus the final prompt or prompt set and whether the built-in tool or fallback CLI mode was used.

## Transparent image requests

Ask built-in `image_gen` for a genuinely transparent background and preserve its alpha.

## Prompt augmentation

Reformat user prompts into a structured, production-oriented spec. Make the user's goal clearer and more actionable, but do not blindly add detail.

Treat this as prompt-shaping guidance, not a closed schema. Use only the lines that help, and add a short extra labeled line when it materially improves clarity.

### Specificity policy

Use the user's prompt specificity to decide how much augmentation is appropriate:

- If the prompt is already specific and detailed, preserve that specificity and only normalize/structure it.
- If the prompt is generic, you may add tasteful augmentation when it will materially improve the result.

Allowed augmentations:
- composition or framing hints
- polish level or intended-use hints
- practical layout guidance
- reasonable scene concreteness that supports the stated request

Not allowed augmentations:
- extra characters or objects that are not implied by the request
- brand names, slogans, palettes, or narrative beats that are not implied
- arbitrary side-specific placement unless the surrounding layout supports it

## Use-case taxonomy (exact slugs)

Classify each request into one of these buckets and keep the slug consistent across prompts and references.

Generate:
- photorealistic-natural — candid/editorial lifestyle scenes with real texture and natural lighting.
- product-mockup — product/packaging shots, catalog imagery, merch concepts.
- ui-mockup — app/web interface mockups and wireframes; specify the desired fidelity.
- infographic-diagram — diagrams/infographics with structured layout and text.
- scientific-educational — classroom explainers, scientific diagrams, and learning visuals with required labels and accuracy constraints.
- ads-marketing — campaign concepts and ad creatives with audience, brand position, scene, and exact tagline/copy.
- productivity-visual — slide, chart, workflow, and data-heavy business visuals.
- logo-brand — logo/mark exploration, vector-friendly.
- illustration-story — comics, children’s book art, narrative scenes.
- stylized-concept — style-driven concept art, 3D/stylized renders.
- historical-scene — period-accurate/world-knowledge scenes.

Edit:
- text-localization — translate/replace in-image text, preserve layout.
- identity-preserve — try-on, person-in-scene; lock face/body/pose.
- precise-object-edit — remove/replace a specific element (including interior swaps).
- lighting-weather — time-of-day/season/atmosphere changes only.
- background-extraction — transparent background / clean cutout. Ask built-in `image_gen` for actual transparency.
- style-transfer — apply reference style while changing subject/scene.
- compositing — multi-image insert/merge with matched lighting/perspective.
- sketch-to-render — drawing/line art to photoreal render.

## Shared prompt schema

Use the following labeled spec as shared prompt scaffolding for both top-level modes:

```text
Use case: <taxonomy slug>
Asset type: <where the asset will be used>
Primary request: <user's main prompt>
Input images: <Image 1: role; Image 2: role> (optional)
Scene/backdrop: <environment>
Subject: <main subject>
Style/medium: <photo/illustration/3D/etc>
Composition/framing: <wide/close/top-down; placement>
Lighting/mood: <lighting + mood>
Color palette: <palette notes>
Materials/textures: <surface details>
Text (verbatim): "<exact text>"
Constraints: <must keep/must avoid>
Avoid: <negative constraints>
```

Notes:
- `Asset type` and `Input images` are prompt scaffolding, not dedicated CLI flags.
- `Scene/backdrop` refers to the visual setting. It is not the same as the fallback CLI `background` parameter, which controls output transparency behavior.
- Fallback-only execution notes such as `Quality:`, `Input fidelity:`, masks, output format, and output paths belong in the CLI path only. Do not treat them as built-in `image_gen` tool arguments.

Augmentation rules:
- Keep it short.
- Add only the details needed to improve the prompt materially.
- For edits, explicitly list invariants (`change only X; keep Y unchanged`).
- If any critical detail is missing and blocks success, ask a question; otherwise proceed.

## Prompting best practices
- Structure prompt as scene/backdrop -> subject -> details -> constraints.
- Include intended use (ad, UI mock, infographic) to set the mode and polish level.
- Use camera/composition language for photorealism.
- Only use SVG/vector stand-ins when the user explicitly asked for vector output or a non-image placeholder.
- Quote exact text and specify typography + placement.
- For tricky words, spell them letter-by-letter and require verbatim rendering.
- For multi-image inputs, reference images by index and describe how they should be used.
- For edits, repeat invariants every iteration to reduce drift.
- Iterate with single-change follow-ups.
- If the prompt is generic, add only the extra detail that will materially help.
- If the prompt is already detailed, normalize it instead of expanding it.
- For CLI fallback only, see `references/cli.md` and `references/image-api.md` for model, `quality`, `input_fidelity`, masks, output format, and output-path guidance.
- For transparent images, ask built-in `image_gen` for actual transparency and preserve its alpha.

## gpt-image-2 guidance for CLI fallback

The fallback CLI defaults to `gpt-image-2`.

- Use `gpt-image-2` for new CLI/API workflows unless the user confirms a different model.
- CLI `gpt-image-2` does not support `background=transparent`; ask before using `gpt-image-1.5` unless the user explicitly requested that model.
- `gpt-image-2` always uses high fidelity for image inputs; do not set `input_fidelity` with this model.
- `gpt-image-2` supports `quality` values `low`, `medium`, `high`, and `auto`.
- Use `quality low` for fast drafts, thumbnails, and quick iterations. Use `medium`, `high`, or `auto` for final assets, dense text, diagrams, identity-sensitive edits, or high-resolution outputs.
- Square images are typically fastest to generate. Use `1024x1024` for fast square drafts.
- If the user asks for 4K-style output, use `3840x2160` for landscape or `2160x3840` for portrait.
- `gpt-image-2` size may be `auto` or `WIDTHxHEIGHT` if all constraints hold: max edge `<= 3840px`, both edges multiples of `16px`, long-to-short ratio `<= 3:1`, total pixels between `655,360` and `8,294,400`.

Popular `gpt-image-2` sizes:
- `1024x1024` square
- `1536x1024` landscape
- `1024x1536` portrait
- `2048x2048` 2K square
- `2048x1152` 2K landscape
- `3840x2160` 4K landscape
- `2160x3840` 4K portrait
- `auto`

- 사용자는 메인 기획자이며 코드를 직접 쓰지 않는다. 결과·영향·여는 순서를 쉽게 설명한다.
- 작업은 **기존 `C:\Users\dua07\GitHub\ChessFighter`의 main에서 직접** 한다. 추가 워크트리는 새 명시 요청이 있을 때만 쓴다.
- 구현·정리 요청은 실제 변경·적절한 검사·main 커밋·푸시까지 완료한다. PR은 요청할 때만 만든다.
- 새 사용자 지시가 과거 브랜치·보존 범위·번호 규칙보다 우선한다. 과거 기록의 "커밋 금지"를 현재 전체 작업 제한으로 오해하지 않는다.
- 사용자 수정본은 덮어쓰기 전에 보존한다. 파일 백업·패치·stash와 현재 main에 적용한 결과를 구분한다.
- **사용자가 Unity나 Steam에서 직접 보고 조작한 것만 '검증됨/성공'이라고 기록한다.** AI 자동 검사·렌더·코드 관찰은 그 근거와 한계를 쓴다.
- UI 자동화가 사용자 입력·Escape로 중단되면 추가 화면 조작을 멈추고 완료된 범위와 남은 범위를 구분한다.
- 공유 캐릭터 물리·카메라·네트워크는 요청 범위 없이 바꾸지 않는다. 파일 정리로 게임 규칙이나 프로토콜을 바꾸지 않는다.

## 4. 절대 규칙 — 어기면 과거에 실제로 사고가 났던 것들

1. **Active Input Handling은 `Input Manager (Old)`(0)로 둔다. Input System 패키지는 설치하지 않는다**(`JY-lobby`, R20: 설치돼 있으면 켤 때마다 백엔드를 켜라는 창이 뜬다). uGUI가 없어서 Both/New로 바꾸면 HUD 클릭과 입력이 전부 죽는다. `InputSettingsGuard`가 자동으로 되돌린다. → [PITFALLS §1](Docs/Environment/PITFALLS.md)
2. **프로젝트는 선택 패키지가 하나도 없어도 컴파일되어야 한다.** Safe Mode에서는 설치 스크립트가 돌지 않는다. 선택 패키지 코드는 전용 asmdef + `versionDefines` + `defineConstraints`로 가둔다. `ENABLE_INPUT_SYSTEM`을 패키지 설치 여부로 쓰지 않는다.
3. **`Packages/manifest.json`·`packages-lock.json`이 바뀌면 Discard하지 말고 커밋한다.**
4. **폴더 하나 = 어셈블리 하나.** `Game`·`Gameplay`는 Steam을 참조하지 않는다. `Core`는 Unity도 참조하지 않는다. → [Architecture/STRUCTURE](Docs/Architecture/STRUCTURE.md)
5. **Steam 초기화·종료 소유자는 `NetworkRuntime` 하나다.** SteamManager를 따로 추가하지 않는다.
6. **HUD에는 기본 테마가 없다.** ScrollView·Dropdown 같은 복합 컨트롤은 보이지 않는다. 평범한 VisualElement만 쓴다.

## 4. 텍스처 기준

1. **단계마다 한 세트를 코스와 미니게임이 같이 쓴다.** 1단계 C·D·A는 정원의 `GC_` 석재·포장·나무를 쓴다. 2단계 B·E·F·J는 홀의 `PR_Palace*`·대리석을 쓴다. 3단계는 새 세트를 G·H·I와 작전 회의실이 같이 쓴다. 같은 단계 안에서 같은 돌이 두 가지 색으로 보이면 안 된다.
2. **반복되는 큰 면은 이어 붙는(타일링) 텍스처**, 장치·소품은 트림 시트나 작은 아틀라스를 쓴다. 해상도 제안: 큰 면 2048² 한 장이 2~4 m, 소품 1024². 이 값은 출발점이며 성능 측정 전이다.
3. **베이스 컬러에 그림자·빛을 그려 넣지 않는다.** 단계별 빛(낮/촛불/천창)은 Unity 조명이 만든다.
4. **거칠기:** 석재·대리석 0.8~0.95(과한 거울광 금지), 나무 0.7~0.8, 미니게임 단 0.9 이상(가장 무광), 기능 금 0.45 + 발광, 장식 황동 0.75 안팎. 모두 제안치다.
5. **손때:** 1단계는 정원처럼 정점 색 때·이끼·물자국을 쓴다. 2·3단계 실내는 이끼 없이 때만 약하게 쓰고, 3단계가 가장 깨끗하다.
6. **글자·문장:** 백합·사자 문장은 크림·금(1단계), 크림·남색(2단계), 보라·크림(3단계) 바탕에 넣는다. 파랑·주황 바탕은 팀 소유로 읽히므로 장식에 쓰지 않는다.

## 6. 제작 순서와 Unity 연결

1. **단계마다 하나씩 먼저 만든다: C(1단계)·E(2단계)·G(3단계).** C는 정원과 같은 텍스처 세트로 만들어, 슬롯 1→2로 넘어갈 때 돌·포장이 이어지는지 본다.
2. 공통 껍데기(파사드·옆벽·문 뒤 회랑)를 단계마다 한 벌씩 만들고, 같은 단계의 나머지 게임 소품을 그 위에 끼운다.
3. 제작 위치는 지금 방식을 따른다(제안). 원본은 `ArtSource/PawnRush/MiniGames/<Early|Mid|Late>/`, 내보낸 FBX는 `Assets/Resources/PawnRushMiniGames/<Early|Mid|Late>/`에 둔다.
4. **Unity 연결:** R501에서 `MiniGameModels.cs`를 만들었다(아래 설명은 그 전 기록). 새 게임은 이 파일에 한 함수씩 더한다. 예전 설명: Unity 연결은 코드 작업이 따로 필요하다. 지금 미니게임 그림은 `MiniGamePalaceArt`가 코드로 만든 상자다. 게임 부품(다리 상판·캡스턴 막대·가마 등)은 Play 때 다시 설치되므로, FBX도 코드에서 붙여야 한다. 정원의 `RoyalWaterGardenBuilder.Concept`처럼 "블록아웃 그림 끄기 + FBX 얹기" 연결을 만든다. 첫 FBX(C)가 나오면 그때 만든다.
5. 단계마다 확인할 것: 입구에서 할 일과 팀 문이 읽히는지, 전용 모티프가 다른 단계에 새지 않는지, 기능 금·팀색·빨강의 뜻이 지켜지는지, 겹친 면이 없는지.

**확인 범위:** 이 문서는 컨셉아트·기존 문서·코드의 재질 값을 모은 기준 초안이다. 색과 수치는 제안이며, Unity에서 같은 장면에 놓고 확정한다. 사용자 확인 전이다.

## 1. 만들 단위와 정보의 우선순위

만들 것은 **구역 공통 공간 3벌 + 게임별 교체 소품 10벌**이다. 같은 구역의 다른 미니게임이 뽑혀도 북벽·창·바닥·아치의 건축 언어는 유지한다. C 해자, B 아래층, J 수조처럼 바닥을 바꾸는 게임은 바닥 삽입 부품도 게임별 킷에 포함한다.

| 구분 | 적용 방식 |
|---|---|
| 기존 규칙·수량 | 사용자 원문과 현재 Core·미니게임 코드가 기준. 이미지 때문에 바꾸지 않음 |
| R310·R311 3D 연결 규격 | 원래 초반의 이음매를 중반·후반에 맞춘 기획 제안. 중반·후반 Unity 확정 치수로 취급하지 않음 |
| 이 문서의 새 모듈·재질·LOD | 모델링 시작을 위한 **제안치**. 사용자가 확정하거나 Unity에서 검토한 결과가 아님 |
| 컨셉 이미지 | 전체 인상·건축 형태·표면·장치의 구조를 읽는 자료. 치수 도면·물리 시험 결과가 아님 |

그림은 큰 인게임 예상 전경과 장치·재질 참고를 함께 보여 준다. 실제 제작 전에는 해당 게임의 평면 배치와 장치 축을 별도로 맞춘다. 특히 A의 공유판, C의 전체 폭 해자, B의 남겨 둔 가운데 통로를 보통의 두 팀 소품 배치로 치환하지 않는다.

3D에서는 모든 구역의 **게임 소품**을 끌 수 있고, **주변 장식 숨김은 초반에서만 제공**한다. 초반에서 두 표시를 끄면 건축 껍데기와 교체 킷의 구분을 읽기 쉽다. A는 공유판 중앙 단면, 다른 게임은 백 스테이션 중심 단면을 기준으로 읽는다.

## 2. 공간의 자와 연결

좌표는 Unity 기준 **+z가 북쪽·진행 방향, +y가 위**, 미터 단위다. 그림의 카메라 방향과 무관하다. 미니게임 스테이션의 로컬 u는 북쪽, v는 가로이며 3D 예시에서는 `world z = u + 4`로 연결한다.

| 항목 | 기준 | 모델링에서 지킬 점 |
|---|---|---|
| 폰 | 키 약 1m | 장치 높이·막대·문턱을 폰과 나란히 비교. 사람 크기 실내 가구로 키우지 않기 |
| 입구 | (0,0,0) | 양쪽 경계 석재·바닥 무늬를 정확히 이어 붙이는 기준 |
| 전체 폭 | 44m | 팀 스테이션 중심 x−12·+12. 외벽 두께와 돌출 장식은 플레이 폭을 먹지 않게 바깥으로 |
| 앞길 | z0~4 | 팀으로 갈라지는 자리. 장식 소품·가구로 입구를 좁히지 않기 |
| 두 스테이션 | 각 20×20m, z4~24 | 가운데 폭4m 길. A와 C의 예외는 각 게임 절 참조 |
| 놀이 단 | 바닥 위 +0.4m | 코스 바닥보다 어둡고 무광. 입구 램프, 깃발, 간판이 단과 할 일을 구분 |
| 입구 띠 | 스테이션 u0~2.5 | 승격 발판·진입 공간. 장치 장식이 침범하지 않게 유지(A 시작은 기존 u2 예외) |
| 북벽 구역 | z24~30 | 중앙 닫힌 큰 문 + 좌우 팀 문. 벽은 평면 배경이 아니라 문틀 깊이·상부 구조가 있는 건축 |
| 문 뒤 회랑 | z30~36 | 좌우 문에서 가운데 공통 출구로 합류. 그림의 문 뒤에도 실제 이동 공간을 남기기 |
| 공통 출구 | (0,0,36) | 출구 높이0 유지. 이번 디자인 때문에 왕실 층 계단을 추가하지 않기 |
| 진입 테라스 | 폭12×깊이6m, +1m | 앞 장애물 프리팹 소유. 마지막 강한 장치와 미니게임을 안전하게 분리 |
| 열린 진입 아치 | 안쪽 폭12m, 높이5m 이상 | 미니게임 북쪽 중앙문과 다른 문. 여닫는 장애물을 넣지 않음 |
| 내려가는 계단 | 0.25m×4단 | 보이는 단과 걷는 충돌면은 별개 제작. 래그돌 발이 단에 걸리지 않는지는 후속 Unity 확인 |

후반 장애물·결승 공간은 이번 작업에서 설계하지 않는다. 미니게임 뒤쪽 그림은 연결 방향만 제안하며 슬롯7 결승 방의 확정안으로 쓰지 않는다. 앞 장애물 장소별 소품도 대표 예시이고 해당 프리팹의 실제 복제본이 아니다.

## 3. 세 구역 공통 건축 킷

### 초반 — 왕궁 정문 앞 바깥뜰

크림 석회암을 **각진 큰 블록**으로 쌓고 모서리만 짧게 다듬는다. 왕궁 정면 파사드의 중앙 정문이 가장 큰 덩어리이며, 좌우 작은 팀 문은 멀리서도 출구로 읽혀야 한다. 룩 모양 문루·둥근 창·벽체 기단·세로 벽기둥으로 정면을 나누되, 실루엣이 장난감 체스 성처럼 단순해야 한다.

밝은 크림 포장 위의 어두운 놀이판과 참나무 장치가 초점이다. 벽 위는 크림·금 깃발과 회색 슬레이트를 쓰고, 가장자리에는 낮은 잔디·사이프러스·돌 화분·돌 벤치를 둔다. 맑은 낮, 짧고 부드러운 그림자, 물의 청록 반사가 기본이다. 초반 전체를 지붕으로 덮지 않는다. D의 누각은 부분 처마·목재 지지보로만 차이를 준다.

| 건축 부품 | 조형·표면 | 역할·주의 |
|---|---|---|
| 석회암 벽·기단 | 큰 엇갈림 줄눈, 넓은 무광면, 작은 모서리 깨짐 | 낡은 폐허로 만들지 않음. 올라갈 수 있는 장치처럼 작은 돌출턱을 연속 배치하지 않기 |
| 정문·팀 문 틀 | 묵직한 돌 아치·참나무 문짝·짙은 철물 | 중앙문은 닫힘, 두 팀 문이 실제 통과 경로 |
| 룩 문루·코니스 | 사각 덩어리와 톱니, 짧은 회색 지붕 | 파랑 지붕은 백팀 소유 표시처럼 보이므로 피하기 |
| 정원 가장자리 | 낮은 돌 화분·돌 벤치·삼각형에 가까운 사이프러스 | 플레이판·1m 주변 이동 공간에는 들어오지 않음 |
| 천·문장 | 크림 깃발, 무광 금 왕관 | 팀 진척 깃발을 제외한 장식에는 팀색 금지 |

### 중반 — 아랫궁의 작업·생활 홀

크림 대리석 벽 아래에 짙은 호두나무 판벽 허리를 둔다. 높은 창이 공간을 가로로 비추고, 상부 발코니와 벽등·샹들리에가 실내 깊이를 만든다. 정면 중앙에는 6랭크 왕실 날개 문장, 좌우 팀 문에는 진척 표시를 분리한다. 바닥은 밝은 크림·회색 체크 대리석, 놀이 단은 짙은 청회색이다.

기본 3D 천장 높이는 약13m 제안이며 E의9m 책장 꼭대기에 폰·열람등·카메라 여유가 필요하다. 천장 보·샹들리에가 등반 꼭대기를 관통하지 않게 별도 단면에서 확인한다. 건축 금은 어둡고 무광, 할 일 금은 작고 밝게 유지한다.

| 건축 부품 | 조형·표면 | 역할·주의 |
|---|---|---|
| 판벽 모듈 | 큰 직사각 패널, 깊지 않은 프레임, 바닥 걸레받이 | 낮은 벽에서는 폰과 게임 물체의 윤곽을 분리 |
| 대리석 상벽·창 | 굵은 창틀, 넓은 벽면, 단순한 석재 띠 | 빛나는 세로 금 띠가 할 일처럼 보이지 않게 |
| 2층 발코니 | 두꺼운 슬래브·규칙적인 난간 | 새 지름길로 쓰지 않는 배경. 실제 통과 가능 여부는 그림만으로 정하지 않음 |
| 샹들리에·벽등 | 큰 원형 프레임, 촛불 묶음, 벽 연결 브래킷 | E 진행 표시와 일반 조명은 재질·제어를 분리할 수 있게 구성 |
| 북벽 팀 문 인서트 | B 천막·E 회전책장·F 거울·J 수문옆문 | 문틀은 공유하되 게임별 열리는 부품을 별도 제작 |

### 후반 — 알현실 앞의 왕실 홀

중반보다 높은 대리석 기둥과 천창, 큰 왕관을 단8랭크 정문으로 위계를 올린다. 기본 3D의 약17m 천장은 제안치다. 높은 곳은 보라·크림 깃발과 흰 기물 문장, 묶은 벨벳으로 채운다. 낮은 플레이 영역은 조용하고 단순하게 비워 남색 그림자 속에서도 킹·가마·방패가 분리되게 한다.

크림 대리석 바닥 가운데 보라 러너를 두되, H의 체스판과 둘레1m에는 깔지 않는다. I의 빛줄기 높이에서는 벨벳·황동 장식선을 멀리 둔다. G의 담비털은 느린 칸에만 존재해야 한다.

| 건축 부품 | 조형·표면 | 역할·주의 |
|---|---|---|
| 대리석 기둥·기단 | 굵은 수직 덩어리, 작은 무광 황동 기둥머리 | 기둥 장식이 체스판 기능성 기둥과 혼동되지 않게 바깥 배치 |
| 왕관 정문 | 가장 큰 문틀, 남색 문짝, 상부 왕관 | 중앙 정문은 상징물. 플레이 동선은 좌우 팀 문 |
| 천창·상부 장막 | 긴 창과 정돈된 천 접힘 | 시선 유도용 빛을 플레이 위험 표시와 구분 |
| 보라 러너·깃발 | 넓고 단순한 색면, 흰 기물 문장 | 작은 황금 무늬를 과하게 반복하지 않음 |
| 벽감·수납 | 가마 차고, 기물 상자, 커튼 뒤 공간 | 실제 장치의 대기·출현 위치를 숨길 수 있는 깊이를 확보하는 제안 |

## 4. 색·재질과 장식 밀도

| 재질 역할 | 색·질감 방향 | 분리할 이유 |
|---|---|---|
| 바깥 석회암 | 크림, 큰 면, 거친 무광 | 배경 건축. 놀이 단과 명도 대비 |
| 중반·후반 대리석 | 크림·회색, 굵고 드문 결, 과한 거울광 없음 | 공격·팀 표시가 바닥 반사에 묻히지 않게 |
| 놀이 단 | 초반 슬레이트, 중반 청회색, 후반 남색, 매우 무광 | 밝은 메이플·킹·금 띠가 튀어나오게 |
| 메이플·호두나무 | 따뜻한 밝은 나무 / 짙은 갈색, 읽히는 결 방향 | 기능성 장치의 큰 실루엣과 이동축을 강조 |
| 기능성 금 | 금색 #E2B23C 계열, 작은 밝은 영역 | 잡기·밟기·삽입의 뜻. 켜짐·꺼짐 재질을 독립 제어 |
| 장식 황동 | 더 어둡고 채도 낮은 무광 황동 | 놀이 단 둘레2m에서는 기능성 금과 확실히 차이 |
| 팀 표시 | 하늘색 #3FC1D9 / 주황 #F08A2C 계열의 제안 | 깃발·진척·칠한 칸 테두리·잡은 물체 외곽선에 한정. 캐릭터 팀색 변경 확정 아님 |
| 위험 | 빨강 #E0483B 계열 | 체크 고리·예고만. 장식 천이나 팀 구분에 쓰지 않음 |
| 천·벨벳 | 크림·보라·남색, 큰 접힘 | 작은 천 시뮬레이션을 요구하지 않는 고정 형상 제안 |
| 물·거품 | 청록 해자 / 연한 비눗물, 얇은 수면 | 수면이 보이게 유지. 거품·수련은 주변부 위주 |

표의 색은 제작 팔레트 출발점이다. 실제 조명·톤 매핑에서 다르게 보일 수 있으므로 Unity에서 같은 장면에 놓고 결정한다. 밝기값이나 폴리곤 수를 성능·가독성 검증 결과로 표현하지 않는다.

## 5. 게임별 킷과 상세 장면

수량은 **별도 표시가 없으면 한 팀 스테이션 기준**이다. 한 광장 전체 수량은 대부분 두 배다. 장식 개수는 제안이며 게임 규칙 수량과 구분한다.

### C · 해자 도개교 — 초반

[컨셉 이미지](ConceptArt/R311/01_early_C_moat.png)

- **기준:** 해자는 u12~16, 예시 world z16~20의4m 폭으로 광장44m 전체를 가로지른다. 좌우 작동 도개교1개씩, 중앙에는 들어 올린 채 고정된 장식 다리. 가운데 통로 끝에 낮은 난간이 있어 중앙문으로 바로 갈 수 없음을 보여 준다.
- **기능 킷:** 참나무 권양기 프레임·드럼·큰 톱니·걸쇠, 당김줄과 잡는 금 매듭, 1m 간격 황동 눈금, 걸쇠등3개. 다리 좌우 작은 룩 문루와 회색 지붕. 기존 초반3D 다리 상판4×4.1m는 외형 제작 참고치이며 실제 프리팹 치수는 후속 구현 때 대조한다.
- **장식 세트:** 감은 밧줄, 예비 톱니바퀴, 크림 구명 부표, 돌 화분. 수련은 가장자리 소량. 기능성 줄과 장식 밧줄을 다른 위치·명도로 구분한다.
- **이미지 보정:** 부표는 크림·어두운 중성색으로 보정했다. 장식 부표가 위험 신호처럼 보이면 안 된다. **권양기·줄은 다리 접근축에서 옆으로 빼고 폭4m 진입을 비운다.** 3D는 양팀 바깥쪽 local x−4m에 권양기, x−6m에 걸쇠를 둔 제안이다. 이미지의 정면 배치를 그대로 다리 앞에 놓지 않는다.
- **구조:** 북쪽 둑 힌지 축을 중심으로 상판이 내려간다. 상판·철물·지지사슬·드럼을 따로 제작하고, 줄이 감기는 원인과 다리의 이동 결과가 연결되어 보이게 한다. 중앙 장식 다리는 작동용 팀 다리와 소유·기능을 분리한다.
- **그림에서 읽을 것:** 한 다리는 세워지고 다른 다리는 내려가는 단계, 물을 가로지르는 두 통로, 닫힌 중앙문, 북벽 뒤 통과 방향. 물보다 밝은 청록 유광 소품을 게임판 안에 반복하지 않는다.

### D · 정문 쇠살문 누각 — 초반

[컨셉 이미지](ConceptArt/R311/02_early_D_capstan.png)

- **기준:** 팀마다 캡스턴1개·밀 막대4개·수직으로 오르는 쇠살문1개, 목표8바퀴. 허리 높이 막대 끝30cm가 할 일 금이다. 캡스턴과 문을 잇는 사슬은 약2.5m 위에서 지나가는 장식 경로다. 3D의14초 재생은 설명용 연출이다.
- **기능 킷:** 쇠띠를 두른 참나무 드럼, 금 왕관 뚜껑, 막대4개, 바닥 슬레이트 원판과 황동 회전 화살표, 상부 도르래, 사슬, 문 양옆 수직 가이드. 쇠살문 상부 왕관은 장식 황동으로 낮춘다.
- **장식 세트:** 예비 막대 걸이, 사슬 더미, 투구를 둔 벤치, 돌 화분. 누각 처마·기둥은 원을 그리며 미는 영역 밖에 둔다.
- **구조:** 드럼은 수직축으로 회전, 문은 수직 이동, 사슬은 시각 연결이다. 각각 메시·피벗을 분리한다. 문을 밀면 열리는 일반 여닫이문처럼 모델링하지 않는다.
- **그림에서 읽을 것:** 낮고 둥근 수평 운동과 길고 높은 수직 운동의 대비. C와 달리 물·내려가는 다리 없이 쇠와 올라가는 창살이 주제다.

### A · 정문 의장 광장 — 초반

[컨셉 이미지](ConceptArt/R311/03_early_A_parade.png)

- **기준:** **공유8×8판1개**, 18×18m, 한 칸2.25m. 예시 좌표 x−9~9·z6~24. 두 팀 별도 판으로 나누지 않는다. 광장44m 전체가 판인 것도 아니다. 양쪽 스테이션 일부와 가운데 동선을 한 판이 가로지른다.
- **기능 킷:** 칠 전 슬레이트64칸(#4A5060), 흰 석회암·검은 현무암 칠 상태, 얇은 금 줄눈, 칸별 팀색 테두리, 둘레 랭크·파일 글자와 점등 면. 칠 번짐·붓 결은 표면 표현으로 분리한다.
- **장식 세트:** 백·흑 칠통, 붓 걸이, 말린 카펫, 돌 화분. 옆쪽 깃대 열과 낮은 돌 관람석. **판 둘레1m는 비움**.
- **구조:** 바닥64칸은 개별 상태를 표현할 수 있게 재질·인스턴스 구분을 남긴다. 바닥 충돌은 줄눈 없는 단순한 평면으로 만들 수 있는 형태를 제안한다. 장식 화분으로 공유판을 둘로 가르지 않는다.
- **그림에서 읽을 것:** 비어 있는 큰 판의 탁 트임, 아직 바랜 칸과 칠해진 칸의 대비, 두 팀이 같은 판에서 움직이는 관계. 판이 체스 기물을 배치한 대국판처럼 바뀌면 안 된다.
- **실제 조작:** A는 판 위에 서서 칠하는 게임이다. 붓·칠통은 주변 소품이고 폰에게 붓질 조작이나 도구를 추가하는 제안이 아니다. 칠한 흑팀 칸은 검은 현무암 바탕에 주황 테두리이며 칸 전체를 주황색으로 바꾸지 않는다.

### B · 보수 중인 동관 — 중반

[컨셉 이미지](ConceptArt/R311/04_mid_B_repair.png)

- **기준:** 스테이션 안 u6~16의10m 틈, 판자2열×5줄=10장. 한 판자2.5×2m. 판자 더미는 u3·v±8의2곳. 가운데4m 통로는 멀쩡하게 남는다.
- **기능 킷:** 잘린 마루 단면·장선·판자·금 못 머리·놓을 자리, 아래층 비계, 걷히는 팀 문 먼지막이 천. 판자의 긴 결·절단 끝·쇠못을 읽히게 한다.
- **장식 세트:** 톱질 받침, 공구 상자, 칠통, 말린 먼지막이 천. 작은 파편·톱밥은 충돌체 없는 시각 표현 제안이다.
- **구조:** 판자가 놓이는 높이와 바닥 단차를 맞춘다. 아래층은 깊이·낙하를 보여 주는 배경이며 비계를 타고 우회하는 계단으로 만들지 않는다. 아래층 비계의 못오름 처리 필요는 후속 구현 항목이다.
- **이미지 보정:** 폰의 망치질 자세는 설치 완료 연출의 참고이고 새 망치 조작을 요구하지 않는다. 옆벽의 좁은 장식턱·비계도 우회 불가 대상으로 검토한다. 단면에 약3m 같은 깊이 문구가 있어도 생성 이미지의 제안일 뿐 확정값이 아니며, 아래층 깊이는 3D·치수표를 기준으로 후속 구현 때 맞춘다.

## 6. 재사용 모듈 제안

다음은 제작을 시작하기 위한 **제안치**이며 확정 레벨 수치가 아니다. 기존 `ArtSource/PawnRush`의4m 벽·4.5m 바닥 모듈과 연결할 수 있도록 큰 단위를 유지한다. 폭44m와 개별 문틀에 맞지 않는 나머지는 끝단·코너 부품으로 해결하고 놀이판 치수를 억지로 늘리지 않는다.

| 모듈 | 제안 단위 | 조립 방식 |
|---|---|---|
| 초반 벽 | 폭4m×높이3m, 두께약1m | 기본·코너·기단·끝단·톱니를 분리. 하부 접합 기준은 바닥 |
| 바닥 | 외부4.5m 단위와 내부4m 단위 중 해당 킷 기준 선택 | A2.25m 칸, J/G2.05m 칸은 기능 규격이므로 일반 바닥 모듈과 별도 |
| 판벽 | 폭2m/4m, 높이약3m | 기본·문 접합·코너·걸레받이. 상부 대리석과 재질 분리 |
| 상부 벽·창 | 폭4m 단위, 창 인서트 | 창틀·유리/빛 면·벽·기둥을 나눔. E 꼭대기 시야 확인 후 높이 결정 |
| 발코니 | 4m 직선·코너·끝단 | 슬래브·난간·지지보 분리. 배경 영역으로 유지 |
| 기둥 | 기단·몸통·기둥머리3부품 | 구역별 높이 조절. 비균등 축척으로 돌 문양이 늘어지지 않게 |
| 문 | 문틀·문짝·상부 문장·진척 표시 | 통과 폭·높이는 실제 게임 기준과 맞춘 뒤 고정. 이미지 비례만으로 확정하지 않음 |

| 장식 세트 | 게임별3~4종 | 공통 돌 화분 등은 공유, 고유 소품은 입구 안쪽 교체 세트로 관리 |

벽은 바닥 중앙 또는 모서리 중 하나의 스냅 규칙을 킷 전체에 통일한다. 길이가 달라지는 석재 띠는 양 끝 마감·중간 반복을 분리한다. 같은 문틀에 책장·거울·창살을 끼울 수 있도록 문 인서트의 기준점을 통일하는 방식을 제안한다.

## 7. 메시·충돌·동적 축의 분리

공간을 한 덩어리로 합쳐 생성하거나 전체 방을 하나의 복잡한 충돌 메시로 쓰지 않는다. 다음 구분은 모델링 파일의 컬렉션·오브젝트 구분 제안이며 새 Unity 태그나 컴포넌트를 추가한 상태가 아니다.

| 구분 | 포함할 것 | 분리 이유 |
|---|---|---|
| `ENV_` | 벽·바닥·기단·지붕·고정 문틀 | 재사용·조립·카메라 가림 처리 |
| `DEC_` | 책·컵·밧줄 더미·천·작은 철물 | 충돌·잡기·등반과 무관한 장식. 필요에 따라 개수와 표시 거리 조절 |
| `MOV_` | 다리·캡스턴 막대·창살·회전문·가마·수레·침대 | 정해진 축으로 움직일 부품. 원래 게임 이동 방식과 연결 |
| `FX_` | 금 고리·열람등·체크 빛줄기·거품·칠 번짐 | 게임 상태에 따라 켜고 끄는 시각물. 장식과 합치지 않음 |
| `COL_` | 단순 상자·원통·경사면 등 충돌 표현용 참고 | 울퉁불퉁한 줄눈·책등·바퀴·천 때문에 래그돌이 걸리지 않게 |
| `PIV_` / `SOCKET_` | 축·힌지·연결 끝점·도착점·빛줄기 시작점 | 다른 모델러·후속 구현자가 장치의 기준을 잃지 않게 |

| 장치 | 피벗 제안 | 반드시 남길 연결점 |
|---|---|---|

| C 권양기 | 드럼 중심의 가로 회전축 | 줄 시작·걸쇠등·잡는 부분 |

모든 피벗은 Blender 등 원본 파일과 Unity로 내보낸 결과에서 방향을 함께 확인한다. 축 이름만 보고 임의로90도 회전시키지 않는다. 좌우 팀용을 만들 때 음수 스케일을 최종 메시로 남기는 대신, 반전 결과의 법선·피벗·재질 방향을 확인하는 제작 과정을 제안한다.

## 8. 재질 슬롯·LOD·내보내기 제안

- **재질 슬롯:** 석재/목재/철/장식 황동/기능성 금/팀 표시/꺼진 등/켜진 등/천/물·유리를 역할별로 분리한다. 같은 색이라는 이유로 체크 경고와 팀 재질을 합치지 않는다. 문 진척·팀 깃발·열람등처럼 게임에서 제어할 면은 독립 교체가 가능해야 한다.
- **표면 디테일:** 멀리서 읽을 실루엣과 큰 베벨을 먼저 모델링한다. 책 글자·작은 못·돌 미세 균열·나뭇결은 텍스처·노멀로 처리할 수 있는 제안이다. 바닥 줄눈은 실제 깊은 홈을 파지 않아도 된다.
- **LOD:** LOD0은 가까운 장치·단면, LOD1은 중간 거리, LOD2는 큰 실루엣 위주로 제안한다. 초기 감소 비율은 약100/45/15%를 출발점으로 삼되 성능 보장치가 아니다. 작은 못·책 반복·사슬 고리는 먼저 단순화한다. 금 손잡이·체크 고리·목표등·팀 표시 같은 규칙 단서는 먼 거리에서도 갑자기 사라지면 안 된다.
- **충돌:** 벽은 상자, 드럼은 단순 원통, 상판·방패는 상자 등 큰 형태로 제안한다. 시각 LOD와 판정 충돌체를 함께 켰다 끄지 않는다. 장식 비계·벽 책장·발코니의 등반 가능 여부는 별도 Unity 설정과 플레이 확인이 필요하다.
- **폴리곤 예산:** 이미지에서 적정 폴리곤 수·프레임을 추정하지 않는다. 공통 킷을 조립한 뒤 목표 PC·실제12명 환경에서 성능을 재고 예산을 확정한다. 이번 산출물에는 그러한 성능 측정이 없다.
- **내보내기:** 미터 단위·일관된 축·바닥 기준점·적용된 스케일을 유지한다. 메시 이름은 영어로 예: `PR_Early_Wall_4m_LOD0`, `PR_C_BridgeDeck`, `PR_E_ShelfTower_9m`. 기존 프로젝트의 임포트 방식과 재질 경로를 대조한 뒤 적용한다.

## 9. 제작 순서와 확인할 장면

1. 초반 C·중반 E·후반 G를 대표로 잡고 공통 건축3벌의 큰 덩어리만 조립한다.
2. 폰1m 기준 인형을 넣고 입구·팀 문·뒤 회랑·장치 높이·카메라 가림을 맞춘다. 장식 전 상태에서 공간을 읽을 수 있어야 한다.
3. 각 게임의 수량·축·기능성 금을 넣고 시작/중간/완료 상태를 만든다. A는 공유판, C는 전체 폭 물, B는 중앙 통로를 별도 확인한다.
4. 나머지7종 소품을 같은 껍데기에 교체해 넣는다. 배경 재질은 공유하고 게임의 고유 실루엣을 우선한다.
5. 입구 안쪽3~4개 소품·상부 건축·천·조명을 넣는다. 팀색·금·빨강의 의미가 유지되는지 다시 본다.
6. 후속 Unity 작업에서 이동·등반·잡기·충돌·문 열림·온라인·성능을 확인한다. 이번 컨셉·3D가 그 확인을 대신하지 않는다.
