## 5. 일하는 규칙

**브랜치와 병합**
- 각자 `JY-lobby`에서 갈라진다: `PR-match`(A), `PR-course`(B), `PR-promotion`(C). 끝나면 `JY-lobby`로 PR, 병합은 메인 기획(사용자)이 한다.
- `PawnRush.unity`는 **A만** 고친다. B는 코스를 데이터(JSON)로, C는 장치를 프리팹으로 만든다. 그래야 씬 충돌이 없다.
- **R18 주의:** `JY-lobby` 규칙상 이 브랜치에서는 캐릭터 조작·물리(래그돌)를 바꾸지 않는다. C3·C6처럼 래그돌 코드를 고쳐야 하는 작업은 시작 전에 메인 기획에게 "폰 러시 공정성 규칙은 `JY-lobby` 계열에서 고친다"는 허락을 받는다.
- 네트워크 약속이 바뀌면 `SteamSession.Protocol`을 올린다. 이때 세 사람 빌드가 서로 안 맞게 되니 단톡에 알린다.

|---|---|---|
| 저장소 코드 구현·테스트·커밋 | ✅ 주로 여기서. `HANDOFF.md`를 자동으로 읽는다 | — |
| 규칙 명세·수치 표·장애물 기획서 초안 | 검토 | ✅ 초안 |
| 스킬 후보, 밸런스 아이디어 | 검토 | ✅ |
| 코드 리뷰 두 번째 의견 | — | ✅ diff를 붙여 넣어 리뷰 |
| 아트·모델링 프롬프트 | — | ✅ |

- **같은 파일을 두 AI가 동시에 고치지 않는다.** Astra의 결과는 문서(`Docs/GameModes/PawnRush/`)로 남기고, 구현은 Opus 5.5 한 곳에서 한다.
- 작업이 끝나면 AI에게 `HANDOFF.md` §8 체크리스트(REQUIREMENTS·HISTORY·이 표 갱신, `Tools/run-tests-linux.sh` 통과)를 시킨다.
- Unity에서 직접 확인하지 않은 것은 "완료"까지만 적는다. "확인"은 사람이 보고 적는다.
